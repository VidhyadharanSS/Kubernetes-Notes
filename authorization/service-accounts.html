Authorisation - Diff types of authentication in k8s, Service Accounts.

SERVICE ACCOUNTS AND AUTHENTICATION​

  • Kubernetes has no built-in user database. Human users authenticate via:

    • TLS certificates
    • External identity providers (OIDC, LDAP/Kerberos via proxies/webhooks)
    • Static password or token files (legacy/unsupported for production)

  • Kubernetes does manage ServiceAccounts, which are the primary identities for non-human clients (pods, automation tools, controllers).

Authentication is always performed by the API server, regardless of the mechanism used.

AUTHENTICATION METHODS IN KUBERNETES​

1. Static Password File (Basic Auth) – Deprecated​

  • CSV format: password,username,uid,"groups"
  • Enabled via: --basic-auth-file=<path>
  • Requires: API server restart.
  • Security: Not secure (plaintext, no rotation). Not recommended for production.

2. Static Token File – Deprecated​

  • CSV format: token,username,uid,"groups"
  • Enabled via: --token-auth-file=<path>
  • Security: No rotation, insecure.

3. ServiceAccount Tokens (Primary Mechanism)​

  • Used by pods and external automation.
  • Represented as bearer tokens in requests.
  • Stored in pods at: /var/run/secrets/kubernetes.io/serviceaccount/token
  • JWT signed by API server private key.
  • Token types:
    1. Projected tokens (short-lived, auto-rotated)
    2. Manually requested short-lived tokens
    3. Legacy secret-based long-lived tokens (deprecated)

4. Client Certificates (TLS Auth)​

  • Strong, recommended for human users and system components.
  • Validated using --client-ca-file.

5. External Identity Providers​

  • OIDC (Google, Azure AD, Okta, etc.)
  • LDAP/Kerberos via external proxy or webhook.
  • Authentication flow is delegated to provider; API server validates tokens.

Important flags:

  • --oidc-issuer-url=
  • --oidc-client-id=
  • --authentication-token-webhook-config-file=

Who interacts with our cluster?​

  • Humans:
    • Administrators (DevOps), developers, SREs via kubectl.
    • Typically use External Identity Providers & TLS Certs.
    • kubeconfig holds the authentication info.
  • Non-Humans:
    • Monitoring, logging, Security, Policy Enforcers, CI/CD, Backup tools.
    • Uses Service Accounts.
    • Bearer tokens are used for authentication.

SERVICE ACCOUNTS IN KUBERNETES​

Why they exist​

  • Provide identities for pods and automation tools.
  • Enable RBAC-based, scoped, auditable access.
  • Avoid misuse of human credentials.

Key properties​

  • Automatically created per namespace (default SA).
  • Pods inherit the namespace’s default SA unless overridden.
  • Specify a ServiceAccount in pods using: serviceAccountName: <sa-name>
  • Disable token mounting: automountServiceAccountToken: false

HOW SERVICEACCOUNTS AUTHENTICATE (POD-TO-API FLOW)​

  1. Pod starts $\rightarrow$ SA token + CA cert are mounted.
  2. Pod connects to API server using HTTPS.
  3. Pod validates server certificate via ca.crt.
  4. Pod sends JWT token in: Authorization: Bearer <token>
  5. API server validates signature using public keys.
  6. Request goes through authentication $\rightarrow$ authorization (RBAC).

Mounted files:

  • token
  • ca.crt
  • namespace

Note: Tokens can be decoded on jwt.io for claims such as sub, iss, aud.

Evolution of ServiceAccount Tokens (Pre vs Post v1.24):​

FeaturePre v1.24v1.24+
Token typeLong-lived secretShort-lived projected
Stored inSecrets in etcdNot stored; generated per request
ExpirationNoneDefault 1 hour
RotationNoneAutomatic (internal)
SecurityWeakStrong (audience, TTL)

TYPES OF SERVICEACCOUNT TOKENS​

1. Bound ServiceAccount Tokens (TokenRequest API)​

  • Automatically issued when a pod is created and uses a ServiceAccount.
  • Short-lived (~1 hour), signed, scoped (via RBAC), and auto-rotated.
  • Recommended default for pods accessing the API server.

2. Manually Requested Tokens​

  • External systems must explicitly request tokens via the TokenRequest API.
  • These tokens do expire and need re-requesting when needed.
  • Best for CI/CD, Terraform, GitHub Actions, and external automation workflows.

3. Legacy (Perpetual) Tokens via Secrets​

  • Manually created by associating a ServiceAccount with a Secret.
  • These tokens never expire, posing security risks.
  • Not recommended due to static nature and security risk.

ACCESS PATTERN FOR NON-HUMAN CLIENTS​

Inside the Cluster:​

  • Agents authenticate with projected SA tokens.
  • Examples:
    • Monitoring: Prometheus, Datadog
    • Logging: Fluent Bit, Loki
    • Security: Falco, Trivy Operator
    • GitOps: ArgoCD, Flux controllers
    • Backup: Velero/Stash controllers

Outside the Cluster:​

  • CI/CD, Terraform, Pulumi.
  • Authenticate using TokenRequest API short-lived tokens.

Agent–Controller Model:​

  • In-cluster agent $\rightarrow$ talks to API server using SA.
  • External UI/console $\rightarrow$ receives data from the agent (does not call API server directly).
  • Examples: Prisma Cloud Console, Velero CLI, ArgoCD UI.

DEMO: SERVICE ACCOUNTS​

Step 1: Create a Service Account for Jenkins​

kubectl create ns jenkins
kubectl create sa jenkins-sa -n jenkins

Step 2: Create ClusterRole and ClusterRoleBinding for Jenkins SA​

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: jenkins-cluster-role
rules:
- apiGroups: [""]
  resources: ["pods", "services", "endpoints"]
  verbs: ["get", "list", "watch", "create", "delete", "patch", "update"]
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "delete", "patch", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: jenkins-cluster-rolebinding
subjects:
- kind: ServiceAccount
  name: jenkins-sa
  namespace: jenkins
  apiGroup: ""
roleRef:
  kind: ClusterRole
  name: jenkins-cluster-role
  apiGroup: rbac.authorization.k8s.io

Step 3: Generate a Manual Long-Lived Token (Deprecated Approach)​

Create a Secret explicitly bound to the Service Account:

apiVersion: v1
kind: Secret
metadata:
  name: jenkins-sa-secret
  namespace: jenkins
  annotations:
    kubernetes.io/service-account.name: jenkins-sa
type: kubernetes.io/service-account-token

Verify:

kubectl describe -n jenkins secrets jenkins-sa-secret

Note: Kubernetes deprecated automatic long-lived token creation in version 1.24+.

Step 4: Jenkins Requests a Token Using the TokenRequest API (Recommended Approach)​

Manually request a token for jenkins-sa:

kubectl create token jenkins-sa --namespace=jenkins

Alternatively, send a direct API request for token generation:

TOKEN=$(kubectl get secret jenkins-sa-secret -n jenkins -o jsonpath="{.data.token}" | base64 --decode)

curl -X POST "https://<api-server-url>/api/v1/namespaces/jenkins/serviceaccounts/jenkins-sa/token" \
-H "Authorization: Bearer $TOKEN" \
-H "Content-Type: application/json" \
-d '{
  "kind": "TokenRequest",
  "apiVersion": "authentication.k8s.io/v1",
  "spec": {
    "audiences": ["kubernetes"],
    "expirationSeconds": 3600
  }
}'

Step 5: Jenkins Uses the Token to Authenticate​

curl -H "Authorization: Bearer <TOKEN>" https://<api-server-url>/api/v1/pods -k
