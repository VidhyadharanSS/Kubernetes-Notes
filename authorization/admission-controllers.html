Admission Controllers - Built-in & Custom Admission Controllers

ADMISSION CONTROLLERS​

Admission Controllers act as gatekeepers that intercept requests to the Kubernetes API server after the request is authenticated and authorized, but before the object is persisted to etcd.

They are critical for enforcing security, governance, and operational standards. Admission controllers can modify, validate, or reject requests based on custom logic or cluster policies. They apply only to write operations (CREATE, UPDATE, DELETE) and have no effect on read operations (GET, LIST, WATCH).

A typical API request travels through the following phases:​

  1. Authentication (AuthN): Verifies the identity of the requester (User/ServiceAccount).
  2. Authorization (AuthZ): Verifies if the identity has permission to perform the action (e.g., RBAC).
  3. Admission Control: Intercepts the request to validate or modify the object content.
  4. Persistence: If all checks pass, the object is written to etcd.

Key Concept: Admission controllers act as gatekeepers for object persistence. Even if a user has RBAC permissions to create a Pod, an admission controller can reject the request if the Pod configuration violates cluster policy (e.g., trying to run as root).

TYPES OF ADMISSION CONTROLLERS​

1. Mutating Controllers​

  • Action: Modify incoming requests before they are stored.
  • Purpose: Set default values, inject sidecar containers, or alter configuration to meet standards.
  • Order: Executed before validating controllers.

2. Validating Controllers​

  • Action: Inspect requests and accept or reject them. They do not modify the object.
  • Purpose: Enforce compliance, security policies, and quotas.
  • Order: Executed after mutating controllers.

NamespaceLifecycleDisallows operations in nonexistent or terminating namespaces, preventing object creation during namespace teardown.Yes

3. Dual-Function Controllers​

  • Action: Perform both mutation and validation.
  • Example: LimitRanger applies default resource limits (mutation) and checks if limits are within allowed ranges (validation).

CUSTOM ADMISSION CONTROLLERS​

When built-in logic is insufficient, Kubernetes allows the use of Admission Webhooks. These are HTTP callbacks that receive admission requests and return a decision.

Architecture​

  1. Webhook Server: A service (usually running in-cluster) that contains the custom logic.
  2. Configuration: MutatingWebhookConfiguration or ValidatingWebhookConfiguration resources tell the API server where to send requests.
  3. Process:
    • API Server sends the JSON object to the Webhook Server.
    • Webhook Server reviews the object.
    • Webhook Server returns a response: allowed: true/false (for validation) or a JSON Patch (for mutation).

Common Tools:​

  • OPA Gatekeeper: Uses Rego language for policy enforcement.
  • Kyverno: Kubernetes-native policy engine (uses YAML).

CONFIGURATION AND DEFAULTS​

Enabling/Disabling Plugins​

Admission plugins are configured in the kube-apiserver manifest: (/etc/kubernetes/manifests/kube-apiserver.yaml).

  • --enable-admission-plugins: Adds plugins to the default list.
  • --disable-admission-plugins: Removes plugins from the default list.

Example:

--enable-admission-plugins=NodeRestriction,MutatingAdmissionWebhook,ValidatingAdmissionWebhook

Note on Kubeadm/KIND Defaults: In clusters bootstrapped with kubeadm (including KIND), many admission controllers (like LimitRanger, DefaultStorageClass, ResourceQuota) are enabled by default even if not explicitly listed. You must use --disable-admission-plugins to turn them off.

ADMISSION CONTROLLER EXECUTION SEQUENCE​

The API server executes admission controllers in a strict order:

  1. Mutating Phase:

    • All enabled Mutating controllers run first (serial execution).
    • The object is modified in memory.
    • If a Mutating controller rejects a request, the process stops, and the request fails.

  2. Validating Phase:

    • All enabled Validating controllers run next (serial execution).
    • These controllers check the final state of the object (after all mutations).
    • If any Validating controller rejects the request, the entire request is denied, and nothing is written to etcd.

  3. Persistence:

    • If all controllers pass, the object is persisted to etcd.

OPA: AUTHORIZATION VS. ADMISSION CONTROL​

1. OPA as a Webhook Authorizer (AuthZ)​

  • Stage: Authorization (before Admission).
  • Input Data: Only receives request attributes (User, Group, Namespace, Verb, Resource Type).
  • Blind Spot: It cannot see the content of the object (e.g., Pod image, labels, container specs).
  • Use Case: Context-aware access control (e.g., "Allow access only from corporate VPN IP," "Deny deletions outside business hours").
  • Prevalence: Rare in standard deployments; standard RBAC is usually sufficient.

2. OPA as an Admission Controller (Gatekeeper)​

  • Stage: Admission Control (after AuthZ).
  • Input Data: Receives the full Kubernetes object (Pod specs, Ingress configurations, etc.).
  • Capabilities: Can Validate (Accept/Reject) and Mutate (Modify).
  • Use Case: Governance and Security (e.g., "Reject Pods using images from public registries," "Enforce 'Team' label on all Deployments").
  • Prevalence: Standard for enterprise policy enforcement.
