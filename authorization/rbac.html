Authorisation - RBAC Authorisation in Kubernetes

KUBERNETES - RBAC AUTHORISATION​

RBAC (Role-Based Access Control) regulates access to Kubernetes resources by defining who can perform what actions on which resources and where (namespace or cluster).

RBAC consists of four objects:

RBAC ObjectScopePurpose
RoleNamespaceDefine permissions within a namespace
RoleBindingNamespaceAssign Role/ClusterRole to subjects within a namespace
ClusterRoleClusterDefine cluster-wide or reusable permissions
ClusterRoleBindingClusterBind ClusterRole to subjects cluster-wide

Subjects: Users, Groups, ServiceAccounts.

Namespaced vs Cluster-Scoped Resources:​

Resource TypeExamplesNotes
Namespacedpods, deployments, configmaps, secretsAccess controlled by Role + RoleBinding
Cluster-scopednodes, PVs, namespacesRequire ClusterRole + ClusterRoleBinding

Check resources:

kubectl api-resources
kubectl api-resources -o wide

RBAC VERBS​

VerbMeaning
getretrieve a resource
listlist resources
watchobserve changes
createcreate a resource
updateupdate full resource
patchpartial update
deletedelete one
deletecollectiondelete multiple

Configuration Commands​

To set default namespace:

kubectl create ns dev
kubectl config set-context --current --namespace=dev

EXAMPLE 1 : ROLE + ROLE BINDING​

Role:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: workload-editor
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["create", "list"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["create", "list"]

RoleBinding:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-workload-editor
  namespace: dev
subjects:
- kind: User
  name: seema
  apiGroup: rbac.authorization.k8s.io
- kind: Group
  name: junior-admins
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: workload-editor
  apiGroup: rbac.authorization.k8s.io

ServiceAccount subject format:

- kind: ServiceAccount
  name: sa-name
  namespace: dev
  apiGroup: ""

EXAMPLE 2 : CLUSTER ROLE + CLUSTER ROLE BINDING​

ClusterRole:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list", "watch"]

ClusterRoleBinding:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: bind-node-reader
subjects:
- kind: User
  name: seema
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: node-reader
  apiGroup: rbac.authorization.k8s.io

Important Concept: ClusterRoles Are Reusable​

Binding TypeEffect
RoleBinding + ClusterRolePermissions apply only in the binding namespace
ClusterRoleBinding + ClusterRolePermissions apply across all namespaces

EXAMPLE 3 : CLUSTER ROLE + ROLE BINDING​

ClusterRole:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: elevated-workload-editor
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["create", "delete", "update"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["create", "delete", "update", "patch"]

RoleBinding:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: use-clusterrole-in-prod
  namespace: prod
roleRef:
  kind: ClusterRole
  name: elevated-workload-editor
  apiGroup: rbac.authorization.k8s.io
subjects:
- kind: User
  name: seema
  apiGroup: rbac.authorization.k8s.io

Verify access:​

kubectl auth can-i create pods --namespace=dev --as=seema
kubectl auth can-i get nodes --as=seema

Best Practices​

PrincipleExplanation
Least privilegeGrant only required permissions
Prefer namespace-bound RolesUse Role+RoleBinding unless cluster-wide access is required
Use groups / SAsAvoid binding permissions directly to individuals
Reuse ClusterRolesBind them to namespaces via RoleBindings to avoid duplication
Verify accessAlways test using kubectl auth can-i
SA apiGroup must be emptyMandatory for ServiceAccount subjects
