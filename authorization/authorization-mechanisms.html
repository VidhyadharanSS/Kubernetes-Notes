Authorisation - Authorisation modes & Kubernetes API

AUTHORISATION MODES AND KUBERNETES API​

The Kubernetes API is the primary interface for all cluster operations, enabling interaction with resources like Pods, Services, and Deployments. The API server acts as the central gatekeeper, managing Authentication (AuthN), Authorization (AuthZ), and Admission Control.

  • Kubernetes API: The logical interface (RESTful endpoints) exposing cluster resources.
  • API Server: The physical component (pod/process) that hosts the API. It handles authentication, authorization, schema validation, and admission control before persisting data to etcd.

KUBERNETES API ARCHITECTURE​

The API is a RESTful, resource-based interface utilizing standard HTTP verbs (GET, POST, PUT, DELETE, PATCH).

API Endpoints Overview:​

The API server exposes various paths for different functionalities:

EndpointDescriptionAccess Type
/versionReturns API server version.Unauthenticated
/healthz, /livez, /readyzHealth checks for the API server.Unauthenticated
/apiRoot path for the Core Group (legacy resources).Authenticated
/apisRoot path for Named Groups (modern/modular resources).Authenticated
/metricsExposes Prometheus-format metrics.Authenticated
/logsNot a standalone endpoint. kubectl logs interacts with the Kubelet's /containerLogs/ endpoint.N/A

API Groups: Organizing Resources​

Kubernetes splits resources into groups for modularity and versioning.

1. Core Group​

  • Path: /api/v1
  • YAML Representation: apiVersion: v1
  • Resources: Pods, Services, ConfigMaps, Secrets, Namespaces, PVs, PVCs.
  • Note: The group name is an empty string (""), which is why it does not appear in the YAML apiVersion.

2. Named Groups​

  • Path: /apis/<GROUP>/<VERSION>
  • YAML Representation: apiVersion: <GROUP>/<VERSION>
  • Resources:
    • apps/v1: Deployments, StatefulSets, DaemonSets.
    • rbac.authorization.k8s.io/v1: Roles, RoleBindings.
    • networking.k8s.io/v1: Ingress, NetworkPolicies.

Note: API path format: /<root>/<group>/<version>/namespaces/<namespace>/<resourceType>/<name>

Accessing the API:​

  1. Direct Access (curl): Requires manual certificate management.
    • Example: curl https://<IP>:6443/api --cert client.crt --key client.key --cacert ca.crt
  2. Unauthenticated Access: Useful for health checks.
    • Example: curl -k https://<IP>:6443/healthz
  3. Kubectl Proxy: Creates a local HTTP server that handles authentication and forwards requests to the API server over HTTPS.
    • Command: kubectl proxy -> Access via http://127.0.0.1:8001

AUTHORIZATION IN KUBERNETES​

After Authentication verifies identity, Authorization determines if the identity has permission to perform the requested action.

Context-Aware Decision Factors:​

  • User/Group: Who is making the request.
  • Verb: Action (get, list, create, delete).
  • Resource: Object type (pods, secrets).
  • Namespace: Scope of the resource.
  • API Group: The group the resource belongs to.

Authorization Modes:​

Kubernetes supports pluggable authorization modules. The API server evaluates these modes in the order specified by the --authorization-mode flag.

1. RBAC (Role-Based Access Control)​

The standard for production environments. It grants permissions based on roles assigned to users/groups.

  • Role: Defines permissions within a specific namespace.
  • RoleBinding: Assigns a Role to a user/group/SA within a namespace.
  • ClusterRole: Defines permissions cluster-wide (or for non-namespaced resources).
  • ClusterRoleBinding: Assigns a ClusterRole to a user/group/SA cluster-wide.

2. ABAC (Attribute-Based Access Control)​

  • Mechanism: Uses a static JSON policy file defined at API server startup.
  • Drawback: Any policy change requires restarting the API server.
  • Status: Deprecated; not recommended for production.

3. Webhook Authorization​

Outsources the authorization decision to an external service (e.g., OPA, Gatekeeper).

  • Process: API server sends a JSON payload of the request to a remote endpoint. The endpoint returns Allow or Deny.
  • Use Case: Complex business logic, dynamic rules, or centralized policy management.

4. Node Authorization​

A specialized mode that restricts kubelet permissions.

  • Function: Ensures a kubelet on a specific node can only read/modify resources (Pods, Secrets, ConfigMaps) scheduled on that specific node.
  • Mechanism: Activated automatically; relies on the kubelet's identity.

5. AlwaysAllow / AlwaysDeny​

  • AlwaysAllow: Permits every request. No security.
  • AlwaysDeny: Rejects every request.
  • Use Case: Strictly for testing or debugging; never for production.

CONFIGURATION AND EVALUATION FLOW​

Authorization modes are configured in the API server manifest: /etc/kubernetes/manifests/kube-apiserver.yaml.

Example Configuration: --authorization-mode=Node,Webhook,RBAC

Evaluation Logic​

Modes are checked sequentially. The first module to give a definitive decision halts the chain.

DecisionConsequence
AllowRequest is authorized; process stops.
DenyRequest is rejected; process stops.
No OpinionEvaluation proceeds to the next configured mode.

Authorization Flow Examples​

Scenario: User Seema attempts to Create a Pod​

Configuration: Node, Webhook, RBAC

  1. Node Authorizer: Checks request. Since Seema is not a Kubelet, it returns No Opinion.
  2. Webhook Authorizer: External service checks metadata (time of day, user group, source IP).
    • If policy violated: Returns Deny.
    • If policy valid: Returns No Opinion (or Allow).
  3. RBAC Authorizer: Checks RoleBindings.
    • If Seema has a Role permitting create pods: Returns Allow.
    • If no Role found: Returns Deny.

Webhook Authorization vs. Admission Controllers​

It is critical to distinguish between authorization and admission when using tools like OPA.
