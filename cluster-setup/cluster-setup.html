Cluster Bootstrapping: The kubeadm Architecture

kubeadm is the industry-standard tool for bootstrapping Kubernetes clusters that adhere to best practices. Unlike "magic" installers, kubeadm performs the heavy lifting of certificate generation, control-plane component deployment (as static pods), and RBAC provisioning, while leaving the infrastructure and networking (CNI) to the architect.

0. ARCHITECTURAL PREREQUISITES & FIREWALLS​

In a production environment, the network must be partitioned to follow the principle of least privilege.

0.1 Control Plane (Master) Inbound Requirements​

PortProtocolPurposeLogic
6443TCPKubernetes API ServerRemote management and Worker-to-Master comms.
2379-2380TCPetcd Server API2379: Client; 2380: Peer-to-Peer (Quorum).
10250TCPKubelet APISelf-monitoring and Control Plane-to-Node comms.
10259TCPkube-schedulerInternal health checking.
10257TCPkube-controller-managerInternal health checking.

0.2 Data Plane (Worker) Inbound Requirements​

PortProtocolPurposeLogic
10250TCPKubelet APIControl Plane control over pods.
30000-32767TCPNodePort ServicesExternal entry points for applications.
4789UDPCalico VXLANOverlay Network: Pod-to-Pod traffic across nodes.

1. SYSTEM HARDENING & KERNEL TUNING [ALL NODES]​

Kubernetes expects a specific Linux environment. Failure to tune the kernel results in unpredictable networking and Kubelet crashes.

1.1 Disabling Swap (The Performance Requirement)​

Kubernetes' scheduling logic assumes 100% precision in memory allocation. If the OS swaps memory to disk, the Kubelet cannot accurately track resource usage, leading to stability issues.

sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab

1.2 Kernel Modules & Sysctl​

  • br_netfilter: Enables bridge-layer filtering. Mandatory for the CNI to use iptables to route pod traffic.
  • ip_forward: Essential for the node to act as a router for the Pod network.
# Load modules on boot
echo -e "overlay\nbr_netfilter" | sudo tee /etc/modules-load.d/k8s.conf
sudo modprobe overlay
sudo modprobe br_netfilter

# Tuning parameters
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

2. CRI: THE CONTAINERD RUNTIME [ALL NODES]​

Kubernetes communicates with containerd via the Container Runtime Interface (CRI).

2.1 The Cgroup Driver Dilemma​

There are two cgroup managers: cgroupfs (native to many runtimes) and systemd (native to the OS). They must match. If the OS uses systemd but containerd uses cgroupfs, the node will suffer from "cgroup instability" under load.

Production Configuration:

sudo apt-get update && sudo apt-get install -y containerd

# Generate default config
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null

# 1. ENFORCE SystemdCgroup
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

# 2. PIN the Sandbox (Pause) Image
# This prevents Kubelet from failing if the default registry is unreachable
sudo sed -i 's#sandbox_image = ".*"#sandbox_image = "registry.k8s.io/pause:3.10"#' /etc/containerd/config.toml

sudo systemctl restart containerd

3. INSTALLING THE K8s BINARIES [ALL NODES]​

We pin the versions to ensure cluster homogeneity.

sudo apt-get install -y apt-transport-https ca-certificates curl gpg
sudo mkdir -p /etc/apt/keyrings

# Add Kubernetes v1.32 Repository
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.32/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.32/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list

sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl # Prevent accidental upgrades

4. CONTROL PLANE INITIALIZATION [MASTER ONLY]​

Instead of passing dozens of flags to the CLI, "Bible-grade" setups use a Configuration File. This allows for reproducible cluster creation and advanced settings (like custom SANs).

4.1 The Kubeadm Configuration (kubeadm-config.yaml)​

apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
kubernetesVersion: v1.32.0
controlPlaneEndpoint: "cp-internal.company.io:6443" # Recommended for HA
networking:
  podSubnet: "192.168.0.0/16" # Calico Standard
  serviceSubnet: "10.96.0.0/12"
---
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cgroupDriver: systemd # Explicit sync with containerd

4.2 Executing the Bootstrap​

sudo kubeadm init --config kubeadm-config.yaml --upload-certs

# Post-init: Set up admin access
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

5. CNI: ORCHESTRATING THE NETWORK [MASTER ONLY]​

Until a CNI is installed, all nodes will remain in NotReady status and CoreDNS will stay Pending. We use the Tigera Operator to manage Calico.

5.1 Why the Operator Method?​

Traditional YAML-based CNI installs are difficult to upgrade. The Operator provides a Reconciliation Loop for the network itself, ensuring that if a Calico component crashes, it is automatically repaired.

# 1. Install the Operator
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.30.2/manifests/tigera-operator.yaml

# 2. Define the Installation Logic
cat <<EOF | kubectl apply -f -
apiVersion: operator.tigera.io/v1
kind: Installation
metadata:
  name: default
spec:
  calicoNetwork:
    # Use VXLAN for Cloud Environments (AWS/Azure) where BGP is blocked
    bgp: Disabled
    ipPools:
    - cidr: 192.168.0.0/16
      encapsulation: VXLANCrossSubnet
EOF

6. JOINING THE DATA PLANE [WORKERS ONLY]​

The join command uses a short-lived bootstrap token and a CA certificate hash to establish trust.

# Get the command from the Master
kubeadm token create --print-join-command

# Run on Workers
sudo kubeadm join <MASTER_IP>:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>

7. ARCHITECT'S TROUBLESHOOTING TOOLKIT​

7.1 Cgroup Driver Verification​

If the Kubelet is in a crash-loop, verify the driver:

# Check containerd
cat /etc/containerd/config.toml | grep SystemdCgroup

# Check Kubelet
kubectl get cm -n kube-system kubelet-config -o yaml | grep cgroupDriver

7.2 Inspecting the CRI directly​

Use crictl to troubleshoot image pulls or container starts bypassing kubectl.

# Set the socket path (usually done via /etc/crictl.yaml)
export CONTAINER_RUNTIME_ENDPOINT=unix:///run/containerd/containerd.sock

crictl pods
crictl ps
crictl logs <container-id>

7.3 Verifying Networking (The ping test)​

Once the cluster is up, verify that Pods on Node-A can ping Pods on Node-B. If they cannot, verify that UDP 4789 is open between nodes.

# Run a ping test across nodes
kubectl run pod1 --image=busybox --overrides='{"spec": {"nodeName": "node-1"}}' -- sleep 3600
kubectl run pod2 --image=busybox --overrides='{"spec": {"nodeName": "node-2"}}' -- sleep 3600
kubectl exec pod1 -- ping <IP_OF_POD2>

8. SUMMARY OF CRITICAL FILE LOCATIONS​

  • /etc/kubernetes/manifests/: Location of Static Pods (API Server, ETCD). Changes here result in immediate component restarts.
  • /var/lib/kubelet/config.yaml: The Kubelet's runtime configuration.
  • /etc/kubernetes/pki/: The cluster's "Root of Trust." Contains all X.509 certificates.
  • /run/containerd/containerd.sock: The gRPC gateway between Kubelet and the Container Runtime.
