Upgrading a Multi-node Kubernetes Cluster

1. The Logic of Upgrading​

Kubernetes follows a strict Semantic Versioning (Major.Minor.Patch).

  • Release Cadence: A new Minor version (e.g., 1.33) is released every 4 months.
  • Support Policy (N-2): Only the 3 most recent minor versions receive security patches. If you are on 1.30 and 1.33 is released, 1.30 becomes End-of-Life (EOL).
  • The "No-Skip" Rule: You cannot skip minor versions (e.g., 1.31 to 1.33). You must upgrade incrementally: 1.31 → 1.32 → 1.33.

2. Version Skew Policy (The Safety Guardrails)​

To prevent cluster collapse during a rolling upgrade, components must follow these compatibility rules:

  • kube-apiserver: The "anchor." No other component can be newer than the API server.
  • kube-controller-manager / kube-scheduler: Must match the API server version or be at most one minor older.
  • kubelet (Nodes): Can be up to two minors older than the API server. This allows you to upgrade the Control Plane first while workers continue running.
  • kubectl: Supported within +/- 1 minor version of the API server.

3. Pre-Upgrade Preparation​

Before running any commands:

  1. Backup etcd: Use etcdctl snapshot save.
  2. Backup Manifests: Copy /etc/kubernetes/ to a safe location.
  3. Check CNI/CRI compatibility: Ensure Calico and containerd support the target version.
  4. Verify Capacity: Ensure remaining nodes can handle the load when one node is drained.

4. Step-by-Step Upgrade Procedure​

Step 1: Update the Repository [ALL NODES]​

Kubernetes now uses version-specific repositories. You must point the package manager to the v1.33 path.

# Edit the source list
sudo vim /etc/apt/sources.list.d/kubernetes.list

# Update the line to: 
# deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.33/deb/ /

sudo apt-get update

Step 2: Upgrade the Control Plane [CONTROL PLANE ONLY]​

1. Upgrade kubeadm binary: unhold allows the package to be updated; hold prevents accidental updates later.

sudo apt-mark unhold kubeadm
sudo apt-get install -y kubeadm=1.33.4-1.1
sudo apt-mark hold kubeadm

2. Plan the Upgrade: This checks if the cluster is healthy and capable of upgrading. It lists which components will change.

sudo kubeadm upgrade plan

3. Apply the Upgrade: This updates the static pod manifests for the API Server, Scheduler, and Controller Manager. It also automatically renews the cluster certificates.

sudo kubeadm upgrade apply v1.33.4

4. Upgrade Node Components (Kubelet & Kubectl): The API server is now 1.33, but the local kubelet on the CP node is still 1.32.

sudo apt-mark unhold kubelet kubectl
sudo apt-get install -y kubelet=1.33.4-1.1 kubectl=1.33.4-1.1
sudo systemctl daemon-reload && sudo systemctl restart kubelet
sudo apt-mark hold kubelet kubectl

Step 3: Upgrade Worker Nodes [ONE AT A TIME]​

1. Cordon & Drain (Run from Control Plane):

  • cordon: Marks the node as "SchedulingDisabled."
  • drain: Evicts pods. --ignore-daemonsets is required because DaemonSets are managed by a controller and cannot be "evicted" in the standard way.
kubectl cordon worker-1
kubectl drain worker-1 --ignore-daemonsets --delete-emptydir-data

2. Upgrade Node Configuration (Run on Worker Node): First, update the repository as shown in Step 1, then:

sudo apt-mark unhold kubeadm kubelet kubectl
sudo apt-get update
sudo apt-get install -y kubeadm=1.33.4-1.1

# 'upgrade node' retrieves the latest cluster config from the API server
sudo kubeadm upgrade node

sudo apt-get install -y kubelet=1.33.4-1.1 kubectl=1.33.4-1.1
sudo systemctl daemon-reload && sudo systemctl restart kubelet
sudo apt-mark hold kubeadm kubelet kubectl

3. Uncordon (Run from Control Plane):

kubectl uncordon worker-1

5. Advanced Topic: Draining & Pod Disruption Budgets (PDB)​

As seen in the architectural diagram, a PDB limits the number of pods of a replicated application that are down simultaneously from voluntary disruptions (like a drain).

  • Logic: If your app has 4 replicas and a PDB with minAvailable: 3, the drain command will only evict one pod. It will then wait for a replacement to be Ready on another node before evicting the next.
  • The Trap: If your other nodes are full and the replacement pod cannot schedule, the drain command will hang indefinitely. You must add capacity or relax the PDB to proceed.

6. Calico Troubleshooting (Post-Upgrade)​

Upgrades can sometimes trigger CNI readiness issues, particularly with BGP/Typha.

  • Symptoms: Nodes show Ready, but pods cannot talk to each other. calico-node logs show "BIRD is not ready."
  • The Fix for Cloud (VXLAN): Most cloud providers don't support BGP. Ensure Calico is told to ignore it: 
    kubectl patch installation.operator.tigera.io default --type=merge -p '{"spec":{"calicoNetwork":{"bgp":"Disabled"}}}'
  • Typha Port: In operator-based installs, calico-node connects to calico-typha. Ensure TCP 5473 is open between all nodes in your Security Groups.

7. Key Files Summary for CKA​

  1. /etc/kubernetes/manifests/: Location of static pods (API Server, etc.). kubeadm upgrade apply modifies these.
  2. /var/lib/kubelet/config.yaml: The configuration file for the kubelet on that specific node.
  3. /etc/apt/sources.list.d/kubernetes.list: The source for your K8s binaries.
  4. ~/.kube/config: Your administrative credentials. Always check the server version here vs kubectl get nodes.
