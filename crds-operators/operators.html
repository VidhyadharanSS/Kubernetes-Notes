Kubernetes - Operators

OPERATORS​

As we already know:

  • Custom Resource (CR): A user-defined object that extends Kubernetes functionality (e.g., a BackupPolicy object). It represents the user's intent.
  • Custom Resource Definition (CRD): The schema or blueprint that defines the structure and validation rules of a CR.
  • Custom Controller: A control loop that continuously monitors CRs and reconciles the system's actual state with the desired state defined in the CR.

STATEFUL vs STATELESS APPLICATIONS​

Stateless Applications​

  • Definition: Applications that do not store user data or session information locally within the container.
  • State Management: Relies on external systems like distributed caches (e.g., Redis) or databases.
  • Scalability: Highly flexible. Any pod can handle any request.
  • Resilience: Pods are interchangeable; if one fails, traffic is seamlessly routed to another.

Stateful Applications​

  • Definition: Applications that require internal data storage, persistent identity, or ordered startup (e.g., PostgreSQL, MongoDB, Kafka).
  • Challenges:
    • Data Consistency: Replicas must coordinate to ensure data integrity.
    • Identity: Pods often require stable network identities and persistent storage bindings.
    • Failover: Requires complex logic for leader election and data promotion.
  • Management: Typically utilizes StatefulSets, PersistentVolumeClaims (PVCs), and Headless Services.

The Problem: Manual Management​

Without Operators, managing stateful applications requires extensive coordination between DevOps and Database Administrators (DBAs).

DevOps Responsibilities:

  • Provisioning storage (PVCs/StorageClasses).
  • Managing StatefulSets and internal DNS.
  • Configuring RBAC, Secrets, and ServiceAccounts.
  • Scripting health checks (Probes) and backups (CronJobs).

DBA Responsibilities:

  • Designing replication topologies (Master-Replica).
  • Managing failover promotion workflows.
  • Tuning performance and handling schema migrations.
  • Ensuring data consistency and replication integrity.

The Problem: This manual approach is fragile, labor-intensive, and prone to human error.

WHAT ARE OPERATORS?​

A Kubernetes Operator is a design pattern that codifies human operational knowledge into software to automate the management of complex applications.

Core Function​

An Operator acts as a specialist controller running inside the cluster. It automates the entire lifecycle of an application, including installation, upgrades, scaling, backups, and failure recovery.

Core Components​

  1. Custom Resource Definitions (CRDs): Extends the Kubernetes API to include new resource types specific to the application (e.g., KafkaCluster, MySQLReplicaSet).
  2. Custom Resources (CRs): Instances of the CRD created by users to declare their desired state (e.g., "Deploy a 3-node cluster").
  3. Custom Controller: The brain of the Operator. It runs a reconciliation loop that watches CRs and interacts with the Kubernetes API to implement logic (scaling, healing, backing up).
  4. Kubernetes Resources: The standard objects (Deployments, Services, ConfigMaps) created and managed by the Controller to fulfill the CR's requirements.

Logical Hierarchy​

  • The Operator: The overarching pattern containing the logic and definitions.
  • The Controller: Monitors specific CRs.
  • The Action: The Controller reads the CRD, interprets the CR, and creates/updates default Kubernetes resources to match the desired state.

OPERATOR STRUCTURE​

Operator
└── Custom Controller
    ├── Watches: Custom Resources (CRs)
    ├── Reads: Custom Resource Definitions (CRDs)
    └── May create: Default Kubernetes Resources
        ├── StatefulSets / Deployments
        ├── Services / Ingress
        ├── ConfigMaps / Secrets
        └── PVCs, CronJobs, Jobs, etc.

Operators are not limited to databases. They are a general-purpose automation pattern suitable for any scenario requiring the reconciliation of desired state vs. actual state.

Common Use Cases:​

  • Databases: MySQL, PostgreSQL, MongoDB.
  • Monitoring: Prometheus, Thanos.
  • Security: Cert-manager (TLS), Kyverno (Policy).
  • Networking: Istio, Cilium.
  • Backup: Velero.

Operators vs. Helm/Kustomize​

Operators do not replace Helm or Kustomize; they complement them.

  • Helm/Kustomize: Best for templating and installation (Day 1 operations).
  • Operators: Best for lifecycle management and runtime automation (Day 2+ operations).
  • Combined Workflow: Use Helm to deploy the Operator and its Custom Resources; use the Operator to manage the application's ongoing health and state.

DEVELOPING OPERATORS​

Creating an Operator involves building a controller that watches specific resources.

Maturity Model​

A basic Operator might simply deploy resources. A mature, production-grade Operator handles:

  • Backup & Restore: Automated scheduling, validation, and disaster recovery.
  • Reliability: Retries, concurrency handling, and self-healing.
  • Observability: Exporting metrics to Prometheus and updating CR status fields.
  • Dynamic Scaling: Adjusting resources based on load or pressure.

Development Frameworks​

  • Operator SDK (Go): The industry standard for robust, high-performance Operators.
  • Kubebuilder: A scaffolding tool often used within the Operator SDK.
  • Operator SDK (Helm/Ansible): Allows creation of Operators without writing Go code, utilizing existing Charts or Playbooks.
  • Java Operator SDK: For teams integrated into the Java ecosystem.

How Do You Choose?​

If you are...Use this...
A Go developerOperator SDK (Go) or Kubebuilder
Comfortable with HelmOperator SDK (Helm)
Strong in Ansible automationOperator SDK (Ansible)
Exploring webhooks/lightweightMetacontroller
Working in a Java ecosystemJava Operator SDK

Note: Go-based Operators (via Operator SDK or Kubebuilder) are the most powerful and widely adopted in production environments.

DEMO: KUBE-GREEN OPERATOR​

The demo illustrates the use of the kube-green Operator, designed to reduce CO2 and costs by scaling down non-critical workloads during off-hours.

Step 1: Install Operator Lifecycle Manager (OLM)​

OLM manages the installation and updates of Operators running in the cluster.

  • Action: Install OLM via the official installation script.

Step 2: Install Kube-Green​

  • Action: Apply the install manifest from OperatorHub.
  • Result: Creates a Subscription and installs the Operator in the operators namespace.

Step 3: Verification​

  • Check the ClusterServiceVersion (CSV) to ensure the status is Succeeded.
  • Verify the CRD sleepinfos.kube-green.com is registered in the API.

Step 4: Deploy Sample Application​

Deploy a standard NGINX Deployment with 2 replicas:

# nginx.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx

Step 5: Configure SleepInfo Policy​

Create a SleepInfo Custom Resource to define the scaling logic:

# sleepinfo.yaml
apiVersion: kube-green.com/v1alpha1
kind: SleepInfo
metadata:
  labels:
    app: kube-green
  name: sleepinfo-sample
spec:
  excludeRef:
    - apiVersion: apps/v1
      kind: Deployment
      name: critical-app
  sleepAt: '17:55'
  wakeUpAt: '08:00'
  weekdays: 0-6
  suspendCronJobs: true
  timeZone: Asia/Kolkata

Key Configuration Fields:

  • sleepAt: Time to scale down (e.g., '17:55').
  • wakeUpAt: Time to restore replicas (e.g., '08:00').
  • weekdays: Days the policy is active (e.g., 0-6 for Mon-Sun).
  • excludeRef: Specific resources to exempt from the policy (e.g., critical production apps).
  • timeZone: The time zone for the schedule (e.g., 'Asia/Kolkata').

Step 6: Observation​

  • Once the SleepInfo CR is applied, the Operator monitors the time.
  • At sleepAt, the Operator scales target Deployments to 0 replicas.
  • At wakeUpAt, the Operator restores the original replica count.
