Network Policies - Basics & Demo

Kubernetes NetworkPolicies are Layer 3 (IP-based) and Layer 4 (Port-based) security rules. They act as a distributed firewall for your pods, allowing you to control traffic flow at a granular level.

By default, Kubernetes operates on an "Allow All" model (non-isolated). NetworkPolicies allow you to transition to a "Zero-Trust" model where only explicitly defined traffic is permitted.

The 3-Tier Application Context​

Standard production architecture for visualization:

  • Frontend (Web Tier): Runs Nginx. Receives external traffic. Needs to talk to the Backend.
  • Backend (Application Tier): Runs application logic (e.g., Python). Receives traffic from the Frontend. Needs to talk to the Database.
  • Database (Data Tier): Runs MySQL. Receives traffic from the Backend. Should NOT be accessible by the Frontend directly.

CNI Enforcement​

NetworkPolicies are declarative. While Kubernetes stores the policy object, the CNI (Container Network Interface) plugin is responsible for the actual enforcement (blocking/allowing packets).

  • CNIs that support Policies: Calico, Cilium, Antrea, AWS VPC CNI, Azure CNI.
  • CNIs that DO NOT support Policies: Flannel, basic Kindnet.

Check Command:

kubectl get daemonset -n kube-system 
# Look for calico-node or cilium-agent

Ingress, Egress, and Statefulness​

  • Ingress: Incoming traffic to a pod (e.g., traffic entering the Backend pod from the Frontend).
  • Egress: Outgoing traffic from a pod (e.g., traffic leaving the Backend pod to reach the Database).
  • Statefulness: Kubernetes NetworkPolicies are stateful. If you allow Ingress from Pod A to Pod B, the return (response) traffic from B back to A is automatically allowed. You do not need a separate Egress rule for the response.

Types of Selectors​

NetworkPolicies use three methods to identify allowed traffic:

  1. podSelector: Identifies pods in the same namespace based on labels. 
    podSelector:
      matchLabels:
        role: backend
  2. namespaceSelector: Identifies pods in different namespaces based on namespace labels. 
    namespaceSelector:
      matchLabels:
        app: app1
  3. ipBlock: Uses CIDR ranges for external sources/destinations outside the cluster. 
    ipBlock:
      cidr: 10.0.0.0/24
      except:
        - 10.0.0.5/32

DEMO: Applying Network Policies for 3-Tier Isolation​

Step 1: Cluster Setup (Kind + Calico)​

Default KIND networking doesn't support policies. Disable Kindnet and install Calico.

# kind-cluster.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  disableDefaultCNI: true

Install Calico:

kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.30.2/manifests/calico.yaml

Step 2: Initial Setup (Labels)​

Create pods in the app1-ns namespace with clear labels:

  • Frontend: role: frontend, app: app1
  • Backend: role: backend, app: app1
  • Database: role: db, app: app1

Step 3: Creation of Network Policies​

1. Database Policy (db-netpol.yaml)​

Goal: Allow only Backend pods to reach the Database on Port 3306.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-policy
  namespace: app1-ns
spec:
  podSelector:
    matchLabels:
      role: db # Target the DB pods
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: backend # Only allow traffic from backend
    ports:
    - protocol: TCP
      port: 3306

2. Backend Policy (backend-netpol.yaml)​

Goal: Allow Ingress from Frontend and Egress to DB and DNS.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-policy
  namespace: app1-ns
spec:
  podSelector:
    matchLabels:
      role: backend
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: frontend
    ports:
    - protocol: TCP
      port: 5678
  egress:
  - to:
    - podSelector:
        matchLabels:
          role: db
    ports:
    - protocol: TCP
      port: 3306
  - to: # Allow DNS resolution
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53

Why Do We Need to Allow DNS in Egress?​

When a pod tries to reach db-svc, it first performs a DNS lookup via CoreDNS (running in kube-system).

If your policy includes policyTypes: [Egress] but doesn't explicitly allow port 53 traffic to CoreDNS, the pod will fail to resolve the service name to an IP, breaking all service-to-service communication.

Evaluation Logic: AND vs. OR​

How you structure your YAML drastically changes security permissions.

Scenario A: AND Logic (Combined in Single Item)​

Traffic is allowed ONLY if it matches the Namespace AND the Pod Label. This is the Best Practice for DNS.

- to:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: kube-system
    podSelector:
      matchLabels:
        k8s-app: kube-dns
  • Meaning: Only talk to CoreDNS inside the kube-system namespace.

Scenario B: OR Logic (Separate List Items)​

Traffic is allowed if it matches the Namespace OR matches the Pod Label. Too Permissive.

- to:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: kube-system
  - podSelector:
      matchLabels:
        k8s-app: kube-dns
  • Risks:
    1. A pod outside kube-system can label itself k8s-app=kube-dns and receive traffic.
    2. Any pod inside kube-system can receive traffic even if it isn't CoreDNS.

Key Takeaways for Prep​

  1. Implicit Deny: Once a policy targets a pod, all traffic not explicitly allowed is blocked.
  2. Namespace Scope: NetworkPolicies only apply to the namespace they are created in (unless using namespaceSelector).
  3. Stateful Nature: Don't write return rules; focus on the initiation of the connection.
  4. DNS Egress: Always include Port 53 rules if using an Egress policy.
  5. Selector Logic: A single list item with multiple selectors is an AND. Separate list items (starting with -) are an OR.
