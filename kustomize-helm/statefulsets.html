StatefulSets - Basics & Demos

1. Introduction to StatefulSets​

StatefulSets are the workload API object used to manage stateful applications. While Deployments are designed for stateless microservices, StatefulSets provide the necessary guarantees for applications requiring a unique identity, persistent data, and a specific deployment order.

Stateful vs. Stateless Applications​

  • Stateless Applications: These are "just code." Every instance is identical and interchangeable. They do not store data locally that needs to survive a restart.
    • Examples: Nginx, standard web APIs.
    • Management: Managed via Deployments.
  • Stateful Applications: These are "code + data." Their behavior depends on previous interactions or stored data. If a stateful pod restarts, it must reconnect to the exact same data volume and retain its unique identity.
    • Examples: Databases (MySQL, PostgreSQL, MongoDB), Distributed Systems (Kafka, Elasticsearch, Zookeeper).
    • Management: Managed via StatefulSets.

2. The Session Management Problem​

In a traditional 3-tier architecture, state management is a major challenge:

  1. Web Tier (Frontend): Can become "accidental stateful" if user sessions (login status, shopping carts) are stored in local RAM. If a pod crashes, the session is lost, and the user is logged out.
  2. Application Tier (Backend): Usually stateless, handling logic and DB communication.
  3. Data Tier (Database): Inherently stateful; the source of truth.

Modern Solution: Externalizing State To improve scalability, state is moved to systems like Amazon ElastiCache (Redis). This allows any frontend/backend pod to fetch session data from a centralized cache, making the application tiers truly stateless and easier to scale.

3. Running a Distributed Database​

A production database cluster usually consists of one Primary node (handles writes) and multiple Replicas (handle reads).

Replication Mechanics: Cloning vs. Syncing​

  1. Initial Cloning: A new replica must first copy the existing dataset (e.g., 100GB). To avoid overwhelming the Primary, a Cascading Clone is used (Replica-2 clones from Replica-1).
  2. Continuous Replication: Once cloned, the replica syncs live changes via a stream (Binlogs or WAL). Most systems use a Star Topology for live sync, where all replicas connect directly to the Primary.

4. Why StatefulSets? (Limitations of Deployments)​

Deployments are unsuitable for stateful workloads because:

  1. Random Naming: Deployments use random hashes (e.g., db-x8j2k). Stateful apps need predictable names (e.g., mysql-0).
  2. Lack of Pod-Level DNS: You cannot target a specific pod in a Deployment via a stable DNS name.
  3. Unordered Rollouts: Deployments may start/stop all pods at once, potentially breaking a database Quorum or Primary election.
  4. Generic Storage: Deployments struggle to ensure Pod A always gets its specific Volume A back after a restart or reschedule.

What happens if a pod crashes in a Deployment? If replica-1 crashes and is rescheduled as replica-4, the Primary DB will consider it a new, unauthorized node and refuse to replicate data to it. Databases rely on fixed identifiers (Hostnames, Server IDs, or Replication Slots).

5. Core Characteristics of StatefulSets​

StatefulSets provide the "Sticky Identity" required for stateful applications:

FeatureDeploymentStatefulSet
Pod NamesRandom (e.g., web-5f69b)Deterministic (e.g., web-0, web-1)
Network IDService IP (Shared)Individual Pod DNS (via Headless Service)
Startup/ShutdownParallel / Non-deterministicOrdered (Sequential 0 to N / N to 0)
Storage MappingShared or ephemeral1:1 Pod-to-Volume "Sticky" mapping
Use CaseStateless APIs, FrontendsDatabases, Kafka, Zookeeper

Important Concepts:​

  • Headless Service: Required to create DNS records for each pod. It is defined by setting clusterIP: None.
    • DNS Format: <pod-name>.<service-name>.<namespace>.svc.cluster.local
  • volumeClaimTemplates: Instead of sharing one PVC, this field automates the creation of a unique PVC for every pod in the StatefulSet.
  • Update Strategy - Partition (Advanced): StatefulSets allow "Partitioned" updates, where only pods with an ordinal greater than or equal to the partition are updated. This allows for canary-style updates of stateful clusters.

6. Persistent Storage: Block Storage & ACID​

  • Block Storage (EBS): Preferred for databases due to low latency and high IOPS.
  • Access Modes:
    • RWO / RWOP (ReadWriteOnce / ReadWriteOncePod): Ensures only one pod can write to the disk at a time, preventing data corruption.
  • ACID Properties: Databases prioritize Atomicity, Consistency, Isolation, and Durability. Block storage ensures that once data is written, it survives power failures.
  • CAP Theorem: StatefulSets help manage Consistency and Availability by maintaining stable nodes during network partitions.

7. Demo 1: Implementation on Amazon EKS​

Step 1: Create the StorageClass​

Use volumeBindingMode: WaitForFirstConsumer to ensure the EBS volume is created in the same Availability Zone (AZ) where the pod is scheduled.

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc-gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
allowVolumeExpansion: true

Step 2: Create Namespace​

kubectl create ns mysql-ha

Step 3: Create a Headless Service​

apiVersion: v1
kind: Service
metadata:
  name: mysql
  namespace: mysql-ha
spec:
  clusterIP: None # Required for Headless
  selector:
    app: mysql
  ports:
    - port: 3306

Step 4: Deploy the MySQL StatefulSet​

This includes pod anti-affinity to ensure pods are spread across different nodes/AZs.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: mysql-ha
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      terminationGracePeriodSeconds: 10
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: mysql
            topologyKey: "kubernetes.io/hostname"
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - containerPort: 3306
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "password123"
        volumeMounts:
        - name: mysql-data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:
  - metadata:
      name: mysql-data
    spec:
      accessModes: ["ReadWriteOncePod"]
      storageClassName: ebs-sc-gp3
      resources:
        requests:
          storage: 5Gi

Step 5: Observe Behavior​

kubectl get pods -o wide  # Verify sequential creation (mysql-0, then mysql-1...)
kubectl get pvc           # Verify unique PVC for each pod

8. Demo 2: Verify PVC Reattachment & Persistence​

Step 1: Identify Pod and AZ​

kubectl get pods -o wide --show-labels

Step 2: Write Data to Pod​

kubectl exec -it mysql-1 -- bash
cd /var/lib/mysql
echo "Persistence Test: CloudWithVarJosh" > persistence_check.txt
exit

Step 3: Simulate Node Failure​

Identify the node hosting mysql-1 and terminate the EC2 instance in the AWS Console.

# Get node name
kubectl get pod mysql-1 -o jsonpath='{.spec.nodeName}'

Step 4: Monitor Rescheduling​

kubectl get pods -w

The pod will move from Unknown/Terminating $\rightarrow$ Pending $\rightarrow$ ContainerCreating. Kubernetes detects the failure and recreates the pod.

Step 5: Verify Data Integrity​

Once the pod is Running, exec back in:

kubectl exec -it mysql-1 -- cat /var/lib/mysql/persistence_check.txt

Step 6: Verify Volume Stability​

The "Age" of the PVC will be much older than the "Age" of the new Pod, confirming the volume was reattached, not recreated.

kubectl get pvc mysql-data-mysql-1

9. Final Summary Checklist for StatefulSets​

  1. Prediction: Pods are named [name]-[ordinal].
  2. Ordering: Deployment is $0 \to (N-1)$. Termination is $(N-1) \to 0$.
  3. Headless Service: Must match the serviceName field in the StatefulSet spec.
  4. Storage: volumeClaimTemplates creates PVCs that persist even if the StatefulSet is deleted (manual cleanup required for safety).
  5. Network Identity: Pods are reachable via pod-name.service-name.
