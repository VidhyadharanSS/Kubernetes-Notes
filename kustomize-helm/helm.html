Helm - Basics & Demos

HELM​

As applications grow, the number of Kubernetes resources increases rapidly. Helm acts as a full application lifecycle manager for Kubernetes.

Challenges Without Helm:​

  • Injecting dynamic values (image tags, ports).
  • Tracking deployments across environments.
  • Applying upgrades without breaking workloads.
  • Rolling back when issues occur.
  • Packaging and distributing applications.

HELM vs KUSTOMIZE:​

FeatureKustomizeHelm
Configuration ManagementPatches and overlaysGo templates with conditionals and loops
Versioned PackagingNoYes
Release TrackingNoYes
Rollback SupportNoYes
DistributionNoChart repositories
Lifecycle ManagementNoInstall, upgrade, delete operations
Hooks and TestsNoYes

Kustomize handles configuration overlays but doesn't support:

  • Versioning or packaging.
  • Rollbacks or release tracking.
  • Distribution to other teams.
  • Dynamic templating.
  • Hooks, tests, or lifecycle events.

CORE COMPONENTS OF HELM​

  1. Chart: A bundle containing everything needed to deploy an application (templates, default values, metadata).
  2. Repository: A place where charts are stored and shared (e.g., Bitnami, Artifact Hub).
  3. Release: A running instance of a chart in your cluster. Each release has its own config, history, and state.

Helm vs Docker Analogy:​

Helm ConceptDocker ConceptDescription
ChartContainer ImagePackaged application definition.
Chart RepositoryImage Registry (Docker Hub)Storage for charts/images.
ReleaseRunning ContainerLive instance in the cluster.

Build, Push, Run Flow:

  • Docker: docker build $\rightarrow$ docker push $\rightarrow$ docker run
  • Helm: helm package $\rightarrow$ helm push $\rightarrow$ helm install

BASIC HELM COMMANDS​

1. Repository Management​

  • Add a repository: 
    helm repo add my-bitnami https://charts.bitnami.com/bitnami
  • List added repositories: 
    helm repo list
  • Search local repositories: 
    helm search repo my-bitnami
    helm search repo my-bitnami | grep -i nginx
    Note: helm search repo searches only locally added repositories (offline).
  • Search Artifact Hub: 
    helm search hub nginx
    Note: helm search hub performs online search across all Artifact Hub publishers.

2. Release Management​

  • Install a chart: 
    helm install my-nginx my-bitnami/nginx
  • List releases: 
    helm list
    helm list -A  # List all releases across all namespaces
  • Check release status: 
    helm status my-nginx
  • View release history: 
    helm history my-nginx
  • Upgrade a release: 
    helm upgrade my-nginx my-bitnami/nginx --set image.tag=1.2.3
  • Rollback a release: 
    helm rollback my-nginx 1  # Rollback to revision 1
  • Uninstall a release: 
    helm uninstall my-nginx

CHART STRUCTURE​

Create a new chart: helm create my-chart

Directory Layout:​

my-chart/
├── Chart.yaml          # Metadata (name, version, description)
├── values.yaml         # Default configuration values
├── templates/          # Kubernetes manifest templates using Go templating
│   ├── _helpers.tpl    # Reusable template helpers
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── NOTES.txt       # Post-install message
│   └── tests/          # Test hooks for validation
└── charts/             # Chart dependencies

HELM - DEMOS

DEMO 1: CREATING OWN HELM TEMPLATE FROM SCRATCH​

Objective: Create a reusable NGINX Chart using NodePort and understand templating.

Step 1: Scaffold Helm Directory​

helm create app1-chart

Delete all auto-generated templates in the templates/ folder.

Step 2: Create templates/deploy.yaml​

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-nginx
  labels:
    app: nginx
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
          ports:
            - containerPort: 80

Step 3: Create templates/svc.yaml​

apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-nginx
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80

Step 4: Configure values.yaml​

replicaCount: 2

image:
  repository: nginx
  tag: "1.22"

Step 5: Verify & Install​

# Lint the chart for errors
helm lint ./app1-chart

# Preview generated manifests (Dry run)
helm template app1 ./app1-chart
helm template app1 ./app1-chart --debug
helm install app1 ./app1-chart --dry-run

# Actual Installation
helm install app1 ./app1-chart

DEMO 2: HELM UPGRADE AND ROLLBACK​

Scenario: Update the NGINX version from 1.22 to 1.23 and test rollback.

  1. Update Chart.yaml: Change version: 0.1.0 to version: 0.1.1 and appVersion: "1.22" to "1.23".
  2. Update values.yaml: Change tag: "1.22" to tag: "1.23".
  3. Upgrade: 
    helm upgrade app1 ./app1-chart
  4. Verification: 
    helm list
    helm history app1
    kubectl get deploy -o wide
  5. Rollback: 
    helm rollback app1 1
    Note: Rollback creates a new revision (e.g., revision 3) rather than deleting history.

DEMO 3: MULTI-ENVIRONMENT DEPLOYMENTS (DEV / STAGE / PROD)​

Goal: Deploy the same chart to multiple namespaces with different configurations.

Strategy:​

  • Single base chart.
  • Multiple values files (values-dev.yaml, values-stage.yaml, etc.).

Example Values Files:​

values-dev.yaml

namespace: dev
replicaCount: 1
image:
  tag: "1.23"

values-prod.yaml

namespace: prod
replicaCount: 3
image:
  tag: "1.22"

Installation Commands:​

helm install app1-dev ./app1-chart -f values-dev.yaml -n dev
helm install app1-stage ./app1-chart -f values-stage.yaml -n stage
helm install app1-prod ./app1-chart -f values-prod.yaml -n prod

Verification & Management:​

# List all releases in all namespaces
helm list -A

# Check specific environment
kubectl get deploy,svc -n dev

# Upgrade only one environment
helm upgrade app1-dev ./app1-chart --set image.tag=1.24 -n dev

# Rollback specific environment
helm rollback app1-dev 1 -n dev
