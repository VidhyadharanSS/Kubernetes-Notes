Image Pull Secrets - Pulling Private Images

In production environments, container images are stored in private registries to protect intellectual property and ensure security. Kubernetes requires explicit authentication to pull these images. This is handled via imagePullSecrets and can be managed at either the Pod level or the ServiceAccount level.

Image Registry, Repository, and Images​

Terminology Clarification:​

  • Image Registry: A centralized service for storing and distributing container images.
    • Public: docker.io, ghcr.io
    • Cloud-Native: Amazon ECR, Azure ACR, Google GCR/Artifact Registry.
    • Self-Hosted: JFrog Artifactory, Sonatype Nexus, GitLab Container Registry.
  • Repository: A named collection of related container images that typically represent different versions of the same application (e.g., ubuntu:20.04, ubuntu:22.04).
  • Image: At its core, an image is just a repository + a specific tag/version.

Component Breakdown:​

ComponentDescriptionExample
RegistryThe centralized service storing images.docker.io, ghcr.io, *.ecr.aws
NamespaceThe owner/organization on the registry.cloudwithvarjosh
RepositoryLogical grouping of related images.my-python-app
TagSpecific version or variant.v1.0.0, stable, latest

Full Image Identifier Syntax: <registry>/<namespace>/<repository>:<tag>

Default Behaviors & Troubleshooting​

Defaults:​

  • Default Registry: Defaults to docker.io (Docker Hub).
  • Default Namespace: Defaults to library/ (for official Docker Hub images).
  • Default Tag: Defaults to latest.
    • Note: Using latest is not recommended for production as it makes rollbacks and version tracking difficult.

ImagePullBackOff:​

When Kubernetes attempts to pull an image from a private registry without valid credentials, the Pod will fail with an ImagePullBackOff or ErrImagePull status.

  • Reason: The Container Runtime Interface (CRI) receives a 401 Unauthorized or Insufficient Scope error from the registry.
  • Debugging: Use kubectl describe pod <pod-name> to view events confirming the authentication failure.

Authentication Mechanism​

Kubernetes does not pull images directly; it delegates the task to the Container Runtime (CRI) like containerd or CRI-O.

  1. The Kubelet identifies the image and any associated imagePullSecrets.
  2. The Kubelet fetches the secret credentials from the API server.
  3. The Kubelet passes these credentials to the CRI.
  4. The CRI authenticates with the registry and downloads the image layers.

Primary Methods to Provide Credentials​

MethodScopeConfiguration
Pod-levelSingle PodDefined in spec.imagePullSecrets in the Pod manifest.
Default ServiceAccountNamespace-widePatch the default SA to include the secret. All Pods in that NS inherit it.
Custom ServiceAccountWorkload-specificCreate a new SA, attach the secret, and use spec.serviceAccountName.

DEMO 1: Build and Push a Private Image​

Step 1: Create app.py​

from flask import Flask
app = Flask(__name__)

@app.route("/")
def home():
    return "Hello, Private Registry!"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

Step 2: Create Dockerfile​

FROM python:3.9-slim
WORKDIR /app
ADD app.py app.py
RUN pip install flask
EXPOSE 5000
CMD ["python", "app.py"]

Step 3: Build and Push​

docker build -t <your-username>/app1:1.0.0 .
docker login
docker push <your-username>/app1:1.0.0

Note: Ensure the repository visibility is set to Private in your Docker Hub settings.

DEMO 2: Authenticate Using Image Pull Secrets (Pod-Level)​

Step 1: Create the Docker Registry Secret​

kubectl create secret docker-registry dockerhub-secret \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<your-username> \
  --docker-password=<your-password> \
  --docker-email=<your-email>

Step 2: Define the Pod Manifest​

apiVersion: v1
kind: Pod
metadata:
  name: private-pod
spec:
  containers:
    - name: app-container
      image: docker.io/<your-username>/app1:1.0.0
  imagePullSecrets:
    - name: dockerhub-secret

DEMO 3: Patch Default ServiceAccount (Namespace Level)​

This method avoids adding imagePullSecrets to every single Pod manifest.

1. Setup Namespace and Secret​

kubectl create ns prod-ns
kubectl create secret docker-registry dockerhub-secret \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<your-username> \
  --docker-password=<your-password> \
  --docker-email=<your-email> \
  -n prod-ns

2. Patch the Default ServiceAccount​

kubectl patch serviceaccount default \
  -n prod-ns \
  -p '{"imagePullSecrets": [{"name": "dockerhub-secret"}]}'

3. Define Pod without imagePullSecrets​

apiVersion: v1
kind: Pod
metadata:
  name: ns-pod
  namespace: prod-ns
spec:
  containers:
    - name: app-container
      image: docker.io/<your-username>/app1:1.0.0

DEMO 4: Use a Custom ServiceAccount​

Step 1: Create Custom SA and Attach Secret​

kubectl create serviceaccount custom-sa -n prod-ns

kubectl patch serviceaccount custom-sa \
  -n prod-ns \
  -p '{"imagePullSecrets": [{"name": "dockerhub-secret"}]}'

Step 2: Deploy Pod using Custom SA​

apiVersion: v1
kind: Pod
metadata:
  name: custom-sa-pod
  namespace: prod-ns
spec:
  serviceAccountName: custom-sa
  containers:
    - name: app-container
      image: docker.io/<your-username>/app1:1.0.0

Best Practices and Security​

  1. RBAC: Restrict get and list permissions on Secrets to only authorized users and ServiceAccounts.
  2. Namespace Isolation: Secrets are namespace-scoped. They do not share across namespaces unless explicitly recreated in the target namespace.
  3. Credential Rotation: Regularly update registry passwords or tokens and update the corresponding Kubernetes Secret objects.
  4. Cloud Native Identity: On AWS/GCP/Azure, prefer using IAM Roles for Service Accounts (IRSA) or Workload Identity to avoid managing static password secrets.
  5. External Secrets: Use tools like HashiCorp Vault or AWS Secrets Manager with the External Secrets Operator to inject credentials into Kubernetes dynamically and securely.
