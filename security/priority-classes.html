Priority Classes - Controlling Pod Pre-emption

PRIORITY CLASS AND POD PRE-EMPTION​

Why Pod Priority and Preemption Exist?​

  • Workload Classification: Not all applications have the same business value. Payment processors (critical) should take precedence over logging agents or development dashboards (non-critical).
  • Resource Management: In a full cluster, if a critical pod cannot find space, the scheduler uses Preemption to reclaim resources from less important pods.
  • Intelligent Scheduling: Priority guides the scheduler's queue; pods with higher priority are processed before those with lower priority.

PRIORITY CLASS​

A PriorityClass is a cluster-scoped object that maps a name to a numeric priority value.

  • Numeric Value: Higher values represent higher priority.
  • Value Range: For user-defined classes, the range is from -2,147,483,648 to 1,000,000,000.
  • Global Default: Only one PriorityClass can be set as globalDefault: true. Pods without an explicit priorityClassName will inherit this value. If no global default exists, the priority of pods without a class is 0.
  • System Classes: Kubernetes reserves values above 2 billion (e.g., 2,000,000,000) for system-critical components like etcd or kube-apiserver. Common ones include system-cluster-critical and system-node-critical.

Preemption Mechanism​

Preemption occurs only when a high-priority pod is unschedulable due to insufficient resources.

  • Eviction Process: The scheduler identifies lower-priority pods whose removal would free up enough resources. It triggers a graceful termination of those pods.
  • Preemption Policy: By default, it is PreemptLowerPriority. However, you can set preemptionPolicy: Never. This allows a pod to move to the front of the scheduling queue (high priority) without being allowed to evict other running pods (non-preempting).

Priority vs. QoS (Quality of Service)​

It is crucial to understand that Priority and QoS are two different mechanisms handled by different components:

FeaturePod PriorityQoS Class
Controlled BySchedulerKubelet
StageDuring pod placement (Scheduling)During runtime (Node pressure)
MechanismPreemption: Evicts lower-priority pods to make room for a new high-priority pod.Eviction: Evicts pods based on requests vs limits during resource pressure (e.g., OOM).
ConfigurationPriorityClass resource and priorityClassName in pod spec.Based on requests and limits (Guaranteed, Burstable, BestEffort).

Key Points to Note:​

  • Cluster-Scoped: PriorityClasses are not restricted by namespaces.
  • Reserved Values: Custom priorities must not exceed 1 billion. Values between 1 billion and 2 billion are reserved for internal Kubernetes use.
  • Runtime Stability: Kubernetes does not proactively evict pods just because a high-priority class was created. Preemption is only triggered by the scheduling attempt of a new pod that cannot otherwise find space.
  • Preemption respects PDBs: The scheduler tries to respect Pod Disruption Budgets (PDBs) when choosing victims, but it is not guaranteed.

DEMO: POD PRIORITY AND PRE-EMPTION​

Step 1: Inspect Cluster Capacity and System Priorities​

Check existing classes used by the control plane.

kubectl get pc
kubectl describe pod -n kube-system <etcd-pod-name>

Step 2: Create PriorityClasses​

Define the priority hierarchy for the cluster.

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000
globalDefault: false
description: "Critical production workloads."
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 10
globalDefault: true
description: "Default for non-critical workloads."

Step 3: Deploy Low-Priority Pods​

Deploy pods that consume a significant portion of the node's CPU to fill the cluster.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: lp-nginx
spec:
  replicas: 5
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        resources:
          requests:
            cpu: "1000m" # 1 vCPU per pod

Step 4: Deploy High-Priority Pods and Observe Preemption​

Deploy high-priority pods with large resource requests to trigger eviction of the low-priority pods.

# 03-high-priority-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hp-nginx
spec:
  replicas: 5
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      priorityClassName: high-priority
      containers:
      - name: nginx
        image: nginx:latest
        resources:
          requests:
            cpu: "3000m" # 3 vCPUs per pod

Step 5: Observe the pods​

kubectl get pods -w

Observation: You will see lp-nginx pods entering the Terminating state as hp-nginx pods move from Pending to ContainerCreating.

Priority Ranges Summary​

-2,147,483,648 - 1,000,000,000User-DefinedStandard workloads (Critical to Batch).

Note on Preemption and Termination​

Pod Preemption respects the terminationGracePeriodSeconds.

  • If Pod A (Priority 1000) needs to preempt Pod B (Priority 500), but Pod B has a terminationGracePeriodSeconds of 300s, Pod A will be marked as "scheduled" (bound to the node) but cannot start its containers until Pod B's slot is physically empty after its grace period.
