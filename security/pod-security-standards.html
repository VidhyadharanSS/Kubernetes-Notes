Pod Security - Security Context & Linux Capabilities

Kubernetes makes running containers easy, but it does not secure them by default. Many container images run as the root user (UID 0), which creates significant risk. Pod Security ensures workloads run with the least privilege necessary, preventing misuse, accidental tampering, and potential container breakout.

Why Pod Security?​

Running containers as root is dangerous because:

  • System Integrity: Root-level processes can modify system files.
  • Escalation: A compromise can lead to full host privilege escalation.
  • Access: Containers may gain unintended access to host resources.
  • Compliance: Violates compliance and least-privilege security principles.

Note: Some images run as non-root by default, but this should not be relied upon. Always enforce security explicitly through pod manifests and cluster policies.

1. SECURITY CONTEXT​

Security Context defines privilege, identity, filesystem access, and escalation behavior for Pods and containers.

Pod-level fields (spec.securityContext)​

These settings apply to all containers inside the Pod.

  • runAsUser: Sets the UID for all containers. (e.g., 1000).
    • Recommendation: Use a non-zero UID to avoid running as root.
  • runAsGroup: Sets the primary GID for container processes. Useful for managing file permissions.
  • fsGroup: Assigns a supplemental GID to all processes. Kubernetes changes the ownership of mounted volumes to this GID and sets the setgid bit.
    • Recommendation: Use this to allow non-root users access to shared mounted volumes.
  • runAsNonRoot: Enforces that the container must run as a non-root user. If the image defaults to UID 0, the Pod will fail to start.
    • Recommendation: Always set to true.

Container-level fields (spec.containers[].securityContext)​

These settings apply to a specific container and override Pod-level settings.

  • allowPrivilegeEscalation: Prevents processes from gaining more privileges than their parent process (e.g., via setuid binaries).
    • Recommendation: Set to false.
  • privileged: Grants the container full host access (all kernel capabilities, device access).
    • Recommendation: Avoid unless absolutely necessary for low-level networking or storage operations.
  • readOnlyRootFilesystem: Mounts the container's root filesystem as read-only.
    • Recommendation: Set to true for stateless apps to prevent tampering. Use volumes for specific writable paths (logs/temp).
  • capabilities: Used to add or drop specific Linux capabilities.

Field Applicability Table​

runAsGroup✅✅Container overrides Pod

2. DEMO: SECURITY CONTEXT​

Manifest: secure-pod.yaml​

apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext: # Pod-level
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    runAsNonRoot: true
  containers:
  - name: app
    image: busybox
    command: ["sh", "-c", "sleep 3600"]
    securityContext: # Container-level
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true

Observations:​

  1. Identity: id command shows UID 1000, GID 3000, and supplemental group 2000.
  2. User Name: whoami fails because UID 1000 has no entry in /etc/passwd.
  3. Filesystem: Writing to / fails due to readOnlyRootFilesystem.
  4. Escalation: Sudo/Privilege escalation attempts are blocked.

3. DEMO: WRITABLE VOLUME WITH fsGroup​

To allow safe writes while keeping the root filesystem read-only (recommended for logs and caches):

Manifest Snippet:​

spec:
  securityContext:
    runAsUser: 1000
    fsGroup: 2000
  containers:
  - name: app
    image: busybox
    securityContext:
      readOnlyRootFilesystem: true
    volumeMounts:
    - name: writable-vol
      mountPath: /writable
  volumes:
  - name: writable-vol
    emptyDir: {}

Result:

  • Writes to / fail.
  • Writes to /writable succeed because fsGroup changed the group ownership of the volume to GID 2000 and the process belongs to that group.

4. LINUX CAPABILITIES​

Linux splits root privileges into granular units called Capabilities. By default, Docker/Kubernetes grant a small subset of these.

Key Points:​

  • Capabilities are configured only under container.securityContext.
  • Best Practice: Drop ALL capabilities and add back only the specific ones required.
  • Running as UID 0 (root) without capabilities does not grant full root power.

Common Capabilities:​

  • NET_ADMIN: Network configuration (e.g., modifying interfaces).
  • SYS_ADMIN: Broad system-level functions (dangerous).
  • SYS_TIME: Modify system clock.
  • CHOWN: Change file ownership.
  • SETUID: Change process UID.
  • DAC_OVERRIDE: Override file permission checks.

5. DEMO: LINUX CAPABILITIES​

Manifest: cap-pod.yaml​

apiVersion: v1
kind: Pod
metadata:
  name: cap-pod
spec:
  containers:
  - name: app
    image: busybox
    command: ["sh", "-c", "sleep 3600"]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL # Drop everything first
        add:
        - NET_ADMIN
        - SYS_TIME

Observations inside the Pod:​

  • Success: NET_ADMIN operations (like bringing down a network interface) may work.
  • Failure: chown operations will fail because CAP_CHOWN was dropped.
  • This demonstrates precise privilege scoping.

Pro-Tips​

  • Precedence: Container-level settings always win over Pod-level settings.
  • Hardening: Use readOnlyRootFilesystem: true whenever possible to ensure immutability.
  • Defaulting: If runAsNonRoot is true but the image doesn't specify a user, the Pod will crash. You must provide runAsUser.
  • Audit: Use tools like kube-score or polaris to check if your manifests have these security fields defined.
  • Standards: Kubernetes now uses Pod Security Standards (PSS) (Privileged, Baseline, Restricted) enforced via admission controllers to replace the deprecated PodSecurityPolicy (PSP).
