Kubernetes Ingress: Host-Based Routing & TLS Integration

1. Core Concepts​

  • Host-Based Routing: Traffic is directed to different backend services based on the Host header of the HTTP request (e.g., iphone.cwvj.click vs. android.cwvj.click).
  • TLS Termination: The Application Load Balancer (ALB) handles the heavy lifting of decrypting HTTPS traffic using an SSL certificate. This offloads the CPU burden from your Pods, allowing them to receive plain HTTP traffic.
  • ACM (AWS Certificate Manager): A service that lets you easily provision, manage, and deploy public and private SSL/TLS certificates.

2. Demo 1: TLS Integration & Custom Domains​

Step 1: ACM Certificate Management​

To ensure browsers do not show "Not Secure" warnings, you must prove domain ownership.

  1. Request Certificate: Go to ACM and request a Public Certificate.
  2. Apex vs. Wildcard:
    • A Wildcard cert (*.cwvj.click) covers subdomains but not the apex domain (cwvj.click).
    • Best Practice: Request a single certificate and add both cwvj.click and *.cwvj.click to it for full coverage.
  3. DNS Validation: ACM will provide CNAME records. Click the "Create records in Route 53" button to automate the validation process.

Step 2: TLS-Enabled Ingress Manifest​

The Ingress Controller reads annotations to configure the ALB for HTTPS.

05-ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-demo2
  namespace: app1-ns
  annotations:
    # ALB Configuration
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/load-balancer-name: cwvj-ingress-demo2
    
    # SSL/TLS Settings
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-2:123456789:certificate/uuid
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
    alb.ingress.kubernetes.io/ssl-redirect: '443' # Auto-redirect HTTP to HTTPS
    
    # Health Check (Must match app path)
    alb.ingress.kubernetes.io/healthcheck-protocol: HTTP
    alb.ingress.kubernetes.io/healthcheck-port: traffic-port
    alb.ingress.kubernetes.io/healthcheck-path: /index.html
    alb.ingress.kubernetes.io/success-codes: '200'
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /iphone
            pathType: Prefix
            backend:
              service:
                name: iphone-svc
                port:
                  number: 80

Step 3: Route 53 Alias Records​

Once the Ingress creates the ALB, it will have a long DNS name (e.g., k8s-default-xxxx.us-east-2.elb.amazonaws.com). You must map your custom domain to it.

  1. Go to Route 53 > Hosted Zones > yourdomain.com.
  2. Create a Record.
  3. Toggle Alias: Yes.
  4. Route traffic to: Alias to Application and Classic Load Balancer.
  5. Select your Region and choose the ALB DNS name generated by the Ingress.

3. Demo 2: Name-Based Subdomain Routing​

This is the standard for hosting multiple distinct applications (e.g., iphone.domain.com and android.domain.com) behind a single entry point.

Step 1: Logic Change​

In host-based routing, each subdomain usually serves from the root / path. You must ensure your applications serve their content (like index.html) from the root directory rather than a nested folder.

Step 2: Host-Based Ingress Manifest​

Instead of one host with multiple paths, we define multiple hosts.

06-host-ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-host-demo
  namespace: app1-ns
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-2:123456789:certificate/uuid
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS": 443}]'
spec:
  ingressClassName: alb
  rules:
    - host: iphone.cwvj.click
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: iphone-svc
                port:
                  number: 80
    - host: android.cwvj.click
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: android-svc
                port:
                  number: 80
    - host: cwvj.click # Apex domain
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: desktop-svc
                port:
                  number: 80

4. Verification Checklist​

  1. Browser Padlock: Click the padlock in the browser; verify the certificate is issued by "Amazon" and matches your domain.
  2. HTTPS Redirection: Enter http://cwvj.click and verify it automatically switches to https://.
  3. ALB Listener Rules: Go to AWS Console > EC2 > Load Balancers > Listeners > HTTPS:443 > Rules. You should see rules mapping Host: iphone.cwvj.click to the specific Target Group.
  4. DNS Propagation: Use dig iphone.cwvj.click to ensure it resolves to the ALB's IPs.

5. Summary Table: Ingress Routing Types​

TypeLogicUse Case
Path-Baseddomain.com/app1, domain.com/app2Microservices sharing a single domain.
Host-Basedapp1.domain.com, app2.domain.comMulti-tenancy or distinct product lines.
TLS/SSLhttps:// via ALB AnnotationsSecure production traffic & compliance.

6. Cleanup (The Cost-Saving Step)​

To avoid residual AWS costs, always delete resources in this specific order:

  1. Delete Ingress: kubectl delete ingress <name>. This triggers the controller to delete the ALB, Security Groups, and Target Groups in AWS.
  2. Delete ACM Certs: Delete certificates only after the ALB is gone.
  3. Delete Route 53 Records: Remove Alias A-records.
  4. Delete Cluster: Finally, run eksctl delete cluster --name <name>.
