Kubernetes Ingress: Comprehensive Guide & Demo

Part 1: Introduction to Ingress​

As applications grow, standard service types like NodePort and LoadBalancer show significant limitations.

Limitations of Standard Service Types​

Service TypeLimitations
NodePortScaling Issues: Managing external traffic to dynamic Node IPs is difficult.
Security: Exposing high-range ports (30000-32767) directly on nodes increases the attack surface.
LoadBalancer (L4)Layer 4 Only: Operates at TCP/UDP level; cannot route based on HTTP headers, paths, or hostnames.
Cost: Each service provisions a dedicated cloud LB (e.g., AWS NLB), leading to high costs.
TLS Overhead: Cannot decrypt HTTPS traffic; TLS termination must happen at the Pod level.

The Ingress Resource​

Ingress is a Kubernetes API object (a declarative YAML configuration) that acts as a Layer 7 (Application Layer) router.

Core Capabilities:

  • Path-based Routing: example.com/api vs example.com/web.
  • Host-based Routing: api.example.com vs web.example.com.
  • TLS/SSL Termination: Handles SSL certificates at the Ingress level so backend apps can receive plain HTTP.
  • Default Backend: A default service can be defined to handle 404s (requests that match no rules).

Note: The Ingress resource is just a "Rulebook." It does not perform routing until an Ingress Controller is installed to act as the "Brain."

Part 2: Ingress Controllers​

An Ingress Controller (IC) is a specialized Pod (or set of Pods) that monitors the API Server for Ingress resources and fulfills the rules.

Roles of the Controller​

  1. Watch: Monitors API server for new/updated Ingress objects.
  2. Translate: Converts YAML rules into LB configuration (e.g., NGINX config or AWS ALB rules).
  3. Health Management: Manages health checks for backend services.
  4. Routing: Directs traffic to the appropriate Service or Pod IP.

Controller Types​

  • Cloud-Native (e.g., AWS Load Balancer Controller): Provisions a managed cloud LB (ALB) where routing and TLS are handled outside the cluster.
  • 3rd-Party (e.g., NGINX, Traefik, HAProxy): The controller runs inside the cluster as a Pod. A single L4 LoadBalancer/NodePort forwards all traffic to this Pod for internal HTTP routing.

Popular Controllers:

  • AWS LBC: Deep integration with EKS, manages ALBs/NLBs.
  • NGINX IC: Most widely used, highly customizable.
  • Contour: Built on Envoy, optimized for multi-team ingress.
  • Istio Ingress Gateway: Part of the service mesh; enables mTLS and fine-grained traffic management.

Part 3: Path-Based Routing Demo (AWS EKS)​

Objective: Use a single AWS Application Load Balancer (ALB) to distribute traffic to multiple backend services based on the URL context path.

Step 1: Provisioning the EKS Cluster​

Using eksctl ensures reproducibility. Note the withOIDC: true field; this is mandatory for the ALB Controller to have permission to create AWS resources via IRSA (IAM Roles for Service Accounts).

eks-config.yaml:

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: cwvj-ingress-demo
  region: us-east-2
managedNodeGroups:
  - name: cwvj-eks-priv-ng
    instanceType: t3.small
    desiredCapacity: 4
    privateNetworking: true
iam:
  withOIDC: true

Apply: eksctl create cluster -f eks-config.yaml

Step 2: Install AWS Load Balancer Controller (LBC)​

  1. IAM Policy: Download and create the policy that allows the controller to manage ALBs. 
    curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.13.3/docs/install/iam_policy.json
    aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam_policy.json
  2. Service Account (IRSA): Create the SA and associate it with the IAM policy. 
    eksctl create iamserviceaccount \
      --cluster=cwvj-ingress-demo \
      --namespace=kube-system \
      --name=aws-load-balancer-controller \
      --attach-policy-arn=arn:aws:iam::<ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
      --approve
  3. Install via Helm: 
    helm repo add eks https://aws.github.io/eks-charts
    helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
      -n kube-system \
      --set clusterName=cwvj-ingress-demo \
      --set serviceAccount.create=false \
      --set serviceAccount.name=aws-load-balancer-controller

Step 3: Deploy Microservices​

Deploy apps with topologySpreadConstraints to ensure High Availability across Availability Zones (AZs).

Microservice snippet (iPhone-app):

spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: ScheduleAnyway
      labelSelector:
        matchLabels:
          app: iphone-page

Step 4: The Ingress Resource (Logic Layer)​

The Ingress manifest tells the LBC to build the AWS ALB.

05-ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-demo1
  namespace: app1-ns
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip # Direct Pod routing
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}]'
spec:
  ingressClassName: alb # Vital: Connects this resource to AWS LBC
  rules:
    - http:
        paths:
          - path: /iphone
            pathType: Prefix
            backend:
              service:
                name: iphone-svc
                port:
                  number: 80
          - path: /android
            pathType: Prefix
            backend:
              service:
                name: android-svc
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: desktop-svc
                port:
                  number: 80

Part 4: Target-Type - ip vs instance​

This is a critical performance setting in AWS EKS.

1. target-type: ip (Preferred)​

  • How it works: The ALB registers individual Pod IPs as targets.
  • Requirement: Requires AWS VPC CNI (default in EKS) which assigns VPC-routable IPs to pods.
  • Benefit: Bypasses NodePort and kube-proxy hops. Fewer hops = lower latency.
  • Flow: User -> ALB -> Pod IP.

2. target-type: instance​

  • How it works: The ALB registers EC2 Worker Nodes as targets.
  • Mechanism: Traffic hits a NodePort on the EC2 instance, is handled by kube-proxy, then routed to a Pod (potentially on a different node).
  • Drawback: Adds network latency and "double-hopping."
  • Flow: User -> ALB -> NodePort -> kube-proxy -> Pod IP.

Part 5: Verification & Cleanup​

Verification​

  1. Kubernetes: kubectl describe ingress ingress-demo1 -n app1-ns. Check the "Address" field for the ALB DNS.
  2. AWS Console: Navigate to EC2 > Load Balancers. Ensure the state is Active and Target Groups are Healthy.
  3. URL Test:
    • http://<ALB-DNS>/iphone -> iPhone Service
    • http://<ALB-DNS>/android -> Android Service
    • http://<ALB-DNS>/ -> Default Desktop Service

Proper Deletion Sequence​

To avoid orphaned resources and residual costs:

  1. Delete Ingress first: kubectl delete ingress ingress-demo1 -n app1-ns. (This allows the LBC to clean up the AWS ALB, Security Groups, and Target Groups).
  2. Delete Cluster: eksctl delete cluster --name cwvj-ingress-demo.
