Kubernetes Gateway API: The Modern Evolution of Ingress

The Kubernetes Gateway API is a SIG-Network project designed to evolve and eventually replace the Ingress API. It provides a more expressive, extensible, and role-oriented model for managing networking in a cluster.

1. Why Evolve? Issues with Existing Ingress​

Before the Gateway API, Ingress was the standard, but it suffered from several architectural flaws:

  • Minimal Specification: Native Ingress only supports basic HTTP/S host and path routing.
  • Annotation Overload: Advanced features like rate limiting, timeouts, retries, and canary splits were never standardized. They were implemented via vendor-specific annotations (e.g., nginx.ingress.kubernetes.io/...).
  • Lack of Validation: The API server does not validate annotations. Typos lead to silent failures.
  • Vendor Lock-in: Annotations are not portable. Switching from NGINX to AWS ALB requires a complete manifest rewrite.
  • Namespace Constraints: Ingress resources are confined to a single namespace. Sharing one Load Balancer across multiple namespaces is difficult and relies on non-standard controller hacks.
  • RBAC Weakness: There is no native way to delegate control of specific paths or hosts to different teams within a single Ingress resource.

2. Core Components: Separation of Concerns​

The Gateway API introduces a resource model that separates infrastructure management from application routing, aligning with three distinct organizational roles:

A. GatewayClass (Infrastructure Provider)​

  • Scope: Cluster-scoped.
  • Role: Acts as a blueprint for Gateway implementations.
  • Function: Defines the controller responsible for the class (e.g., nginx.org/gateway-controller). It is analogous to a StorageClass.

B. Gateway (Cluster Operator)​

  • Scope: Namespace-scoped.
  • Role: Provisions the actual networking infrastructure (Cloud LB or In-cluster proxy).
  • Function: Defines Listeners (port, protocol, hostname) and TLS settings. It serves as the entry point for traffic.

C. Route Objects (Application Developer)​

  • Scope: Namespace-scoped.
  • Role: Defines the logic for how traffic is directed to backend Services.
  • Resources: HTTPRoute, GRPCRoute, TCPRoute, UDPRoute.
  • Logic: Routes attach to Gateways via parentRefs.

3. Advanced Native Features (No Annotations Required)​

Gateway API moves features that previously required annotations directly into the core API spec:

  • Traffic Splitting: Native support for weight-based routing (Canary and Blue-Green deployments).
  • Request/Response Filtering: Built-in ability to modify headers, perform redirects, or rewrite paths.
  • Cross-Namespace Routing: Gateways can attach routes from different namespaces.
  • ReferenceGrant: A security resource that explicitly allows a Route in Namespace A to reference a Service in Namespace B, preventing unauthorized cross-namespace traffic hijacking.

5. Hands-on Demo: NGINX Gateway Fabric on KIND​

Step 1: KIND Cluster Setup​

A specific KIND configuration is required to map a hostPort to a containerPort, allowing local access to the NodePort service.

00-kind-cluster.yaml:

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  extraPortMappings:
  - containerPort: 31000
    hostPort: 31000 # Map local 31000 to cluster 31000

Apply: kind create cluster --name=gateway-api --config=00-kind-cluster.yaml

Step 2: Install Gateway API CRDs​

You must install the standard CRDs before the controller. Note: The CRD version must match the Controller version.

kubectl kustomize "https://github.com/nginx/nginx-gateway-fabric/config/crd/gateway-api/standard?ref=v2.1.0" | kubectl apply -f -

Step 3: Install NGINX Gateway Fabric (NGF)​

helm install ngf oci://ghcr.io/nginx/charts/nginx-gateway-fabric \
  --create-namespace -n ngf-gatewayapi-ns \
  --set nginx.service.type=NodePort \
  --set-json 'nginx.service.nodePorts=[{"port":31000,"listenerPort":80}]'

Verify: Ensure GatewayClass status is ACCEPTED=True.

Step 4: Deploy Backend Applications​

Deploy three Python-based apps (iPhone, Android, Desktop) in the app1-ns namespace.

Deployment Snippet:

spec:
  containers:
  - name: python-http
    image: python:alpine
    command: ["/bin/sh", "-c"]
    args:
    - |
      mkdir -p /iphone && echo '<h1>iPhone Users</h1>' > /iphone/index.html && python3 -m http.server 5678

Step 5: Configure the Gateway Resource​

Defines the entry point on port 80.

05-gateway.yaml:

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gateway
  namespace: ngf-gatewayapi-ns
spec:
  gatewayClassName: nginx
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: All # Allows Routes from any namespace to attach

Step 6: Configure HTTPRoutes​

Maps the Gateway listener to backend services based on path prefixes.

06-routes.yaml:

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: iphone-routes
  namespace: app1-ns
spec:
  parentRefs:
  - name: gateway
    namespace: ngf-gatewayapi-ns
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /iphone
    backendRefs:
    - name: iphone-svc
      port: 80

Step 7: Testing Connectivity​

curl http://localhost:31000/iphone
curl http://localhost:31000/android

6. Key Takeaways & Best Practices​

  1. Role-Based Access: Infrastructure (Gateway) and Routing (HTTPRoute) are managed separately, enabling better team autonomy.
  2. Cross-Namespace Capability: A single Gateway can centralize traffic for the entire cluster while Route objects stay with their respective applications.
  3. Standardization: Advanced routing is handled by the standard API spec, finally eliminating "Annotation Hell."
  4. Status is Truth: Always check the .status field of Gateway and Route objects to ensure they are Programmed, Accepted, or Ready.
  5. ReferenceGrant: Use it whenever a Route needs to point to a Service in a different namespace to maintain a "Zero-Trust" security posture.
