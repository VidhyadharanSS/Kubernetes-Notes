Authentication - Symmetric & Asymmetric Encryption, HTTPS

Before diving into Kubernetes security (RBAC, Secrets, TLS), it’s essential to understand encryption—the backbone of all secure communication.

What is encryption and why do we need it?​

Encryption converts readable data (plaintext) into unreadable (ciphertext) to ensure only authorized access.

Purpose:​

  • Protect sensitive data in transit (network) and at rest (storage).
  • Prevent eavesdropping and tampering.
  • Maintain confidentiality, integrity, and authenticity.

TWO MAIN TYPES OF ENCRYPTION​

1. Symmetric Encryption (Shared Key)​

  • Definition: Uses one secret key for both encryption and decryption.
  • Pros: Fast and efficient — best for large (bulk) data.
  • Risk: If the key is leaked, all data is exposed.
  • Algorithms: AES (Industry standard), ChaCha20 (Mobile-optimized), Blowfish, Twofish, DES.
  • Common Uses:
    • TLS data transfer (post-handshake).
    • Disk & database encryption (AES-256).
    • Encrypted backups, Kubernetes Secrets at rest.
  • Why used for bulk data: High speed + efficient hardware support.

2. Asymmetric Encryption (Public Key Cryptography)​

  • Definition: Uses a key pair: Public key (shared) & Private key (kept secret).
  • Logic: Public key encrypts $\rightarrow$ only the corresponding Private key can decrypt.
  • Usage: Used for authentication, digital signatures, and secure key exchange.
  • Algorithms: RSA (Widely supported), Ed25519 (Modern default), ECC (Faster/compact).
  • Common Uses:
    • TLS Handshake (HTTPS).
    • SSH Authentication.
    • Kubernetes Certificates (x.509).
    • JWT signing, Git commit signing.
    • Sealed Secrets (Vault, etc.).
  • Why use it: Secure communication without needing a pre-shared secret.

ENCRYPTION TYPES: IN-TRANSIT AND AT-REST​

1. Encryption In-Transit​

  • Protects data while moving (client $\leftrightarrow$ server, pod $\leftrightarrow$ pod).
  • Mechanism: Uses TLS / mTLS.
  • Goal: Prevents eavesdropping & Man-In-The-Middle (MITM) attacks.
  • K8s Examples: HTTPS, kubectl $\leftrightarrow$ API server, Istio mTLS.

2. Encryption At-Rest​

  • Protects stored data (volumes, etcd, databases).
  • Mechanism: Uses AES / KMS (Key Management Service).
  • K8s Examples: EBS volume encryption, etcd Secrets encryption.

REAL-LIFE SCENARIOS​

Scenario 1: Symmetric (Disk Encryption)​

  • Tool: BitLocker (AES).
  • One key encrypts & decrypts the laptop disk.
  • Even if the disk is stolen, data is unreadable without the key.
  • Ideal for: Large data, local protection.

Scenario 2: Symmetric Alone Isn’t Enough​

  • Problem: If Seema wants to send encrypted data to a bank, how does the bank get the key?
  • Sending the symmetric key over the internet is insecure (Hacker can intercept it).
  • Result: Need asymmetric encryption to exchange keys safely.

Scenario 3: Asymmetric (SSH Login)​

  1. Step 1: Generate key pair using ssh-keygen.
  2. Step 2: Copy the Public Key onto the home directory of the remote server (~/.ssh/authorized_keys).
  3. Result: You can now log in securely because the server uses your Public Key to challenge you, and only your Private Key (which never leaves your system) can solve it.

Key Extensions:

  • Public: .pub, .crt, .pem
  • Private: .key, .ppk, .pem

Scenario 4: Combining Both (The TLS Handshake)​

HTTPS works by using a "Hybrid" approach: Asymmetric to securely exchange a key, then Symmetric for fast data transfer.

How HTTPS Works:

  1. Browser $\rightarrow$ requests secure connection (pinkbank.com).
  2. Server $\rightarrow$ sends TLS certificate (contains Server's Public Key + CA signature).
  3. Browser $\rightarrow$ verifies certificate via CA public key.
  4. Browser $\rightarrow$ generates a random session key (Symmetric).
  5. Browser $\rightarrow$ Encrypts the session key with the Server’s Public Key $\rightarrow$ sends it.
  6. Server $\rightarrow$ decrypts the session key using its Private Key.
  7. Communication begins using the shared Symmetric session key (fast and secure).

Roles:

  • Certificate Authority (CA): Private key signs the certificate; Browser uses CA's Public key to verify authenticity.

  • Server: Uses Private key to decrypt the session key.

  • Browser + Server: Use the Symmetric Session Key (AES) for actual data transfer.

  • Common DevOps CAs: Let's Encrypt (Automation), DigiCert, Sectigo, AWS ACM.

Key Takeaways:​

  • Symmetric Encryption (AES): Fast, best for data storage & bulk transfer.
  • Asymmetric Encryption (RSA, Ed25519): Secure key exchange & identity verification.
  • TLS: Combines both for HTTPS (secure and fast).
  • SSH: Uses asymmetric for secure remote access.
  • At-Rest & In-Transit: Both must be enabled for a truly secure system.
