Authentication: Encryption, TLS, and Secure Key Exchange

Before diving into Kubernetes security (RBAC, Secrets, TLS), it’s essential to understand encryption—the backbone of all secure communication.

1. What is Encryption?​

Encryption converts readable data (plaintext) into unreadable (ciphertext) to ensure only authorized access.

Purpose:​

  • Confidentiality: Protect sensitive data in transit (network) and at rest (storage).
  • Integrity: Prevent tampering during transmission.
  • Authenticity: Verify the identity of the sender and receiver.
  • Non-repudiation: Prevent a party from denying they sent a message.

2. Two Main Types of Encryption​

Symmetric Encryption (Shared Key)​

  • Definition: Uses one secret key for both encryption and decryption.
  • Characteristics: Fast and efficient — ideal for bulk data.
  • Tooling: AES (Industry standard), ChaCha20.
  • Risk: "Key Exchange Problem"—if the key is intercepted while being shared, all data is exposed.
  • K8s Use Case: Disk & database encryption (AES-256), Kubernetes Secrets at rest.

Asymmetric Encryption (Public Key Cryptography)​

  • Definition: Uses a key pair: a Public key (shared with everyone) and a Private key (kept secret).
  • Logic: Data encrypted with the Public key can only be decrypted by the corresponding Private key.
  • Tooling: RSA, Ed25519, ECC.
  • Primary Tools:
    • ssh-keygen: Specifically for SSH authentication.
    • openssl: The standard toolkit for TLS certificate management and identity validation.
  • Use Case: Authentication, digital signatures, and secure key exchange.

Summary Comparison Table​

FeatureSymmetricAsymmetric
Keys UsedOne shared keyPublic + Private key pair
SpeedVery FastSlower (Mathematical overhead)
SecurityKey sharing is riskySecure exchange (Private key never moves)
Primary UseBulk data encryptionAuthentication, exchanging session keys

3. Encryption Types: In-Transit vs. At-Rest​

Encryption In-Transit​

  • Protects data while moving (client $\leftrightarrow$ server, pod $\leftrightarrow$ pod).
  • Mechanism: Uses TLS (Transport Layer Security) or mTLS.
  • K8s Examples: HTTPS traffic, kubectl $\leftrightarrow$ API server, Istio service mesh.

Encryption At-Rest​

  • Protects stored data (volumes, databases, backups).
  • Mechanism: Uses AES / KMS (Key Management Service).
  • K8s Examples: EBS volume encryption, etcd Secrets encryption.

4. Understanding Infrastructure Roles​

To manage security, you must identify the Client and the Server:

  • Client: The entity that initiates a request (e.g., a Developer running kubectl, or a Pod fetching data).
  • Server: The entity that responds to the request (e.g., the kube-apiserver, or a database like etcd).

5. Deep Dive: How SSH Works (Authentication)​

SSH uses asymmetric encryption to prove identity without sending a password over the network.

Step A: Server Authentication (TOFU)​

  1. When you connect for the first time (ssh user@ip), the server sends its Host Public Key.
  2. TOFU (Trust on First Use): You accept the fingerprint, and it is stored in ~/.ssh/known_hosts.
  3. If the server is reinstalled or spoofed later, the fingerprint won't match, triggering a security warning.

Step B: Client Authentication​

  1. Generate Keys: Use ssh-keygen -t ed25519. This creates a private key (id_ed25519) and a public key (id_ed25519.pub).
  2. Copy Public Key: You place your public key on the server in ~/.ssh/authorized_keys.
  3. The Challenge: The server sends a random string encrypted with your public key. Only your Private Key (which never leaves your local machine) can decrypt it. Once decrypted, you are authenticated.

6. Deep Dive: How TLS/HTTPS Works (The Hybrid Approach)​

HTTPS uses a Hybrid approach: Asymmetric to securely exchange a key, then Symmetric for fast data transfer.

The TLS Handshake Steps:​

  1. Request: Browser/Client requests a secure connection.
  2. Presentation: Server sends its TLS Certificate (contains the Server's Public Key + CA Signature).
  3. Verification: Browser verifies the certificate via a Trusted Certificate Authority (CA).
  4. Key Exchange: Browser generates a random Symmetric Session Key. It encrypts this key with the Server’s Public Key and sends it.
  5. Decryption: The Server uses its Private Key to decrypt the session key.
  6. Secure Tunnel: Now, both sides have the same Symmetric key and use it for fast, encrypted data transfer.

Mutual TLS (mTLS):​

In standard TLS, only the server proves its identity. In mTLS, the client also presents a certificate to the server. This is used extensively in Kubernetes for internal communication (e.g., kubelet $\leftrightarrow$ api-server).

7. Key Management & File Formats​

KMS Best Practices:​

  • HSMs: Use Hardware Security Modules for physical key protection.
  • Cloud KMS: Use AWS KMS or Azure Key Vault for centralized, encrypted storage.
  • Air-Gapped Systems: Keep root CA keys offline.
  • Rotation: Regularly rotate certificates and private keys.

Common File Extensions:​

ExtensionDescription
.pubSSH Public Key (Safe to share).
.key / .pemPrivate Key (Must be kept secret).
.crt / .cerSigned TLS Certificate.
.csrCertificate Signing Request (Sent to a CA to get a cert).

Certificate Types Comparison​

Certificate TypeUse CaseTrust LevelTypical Use
Public CAInternet-facing websites.Trusted by all browsers.Production web apps.
Private CAInternal corporate services.Trusted only within the org.Microservices, K8s internal auth.
Self-SignedLocal development.Not trusted by browsers.Testing, local environment.

Key Takeaways for Prep:​

  1. Symmetric = Speed: Use for bulk data.
  2. Asymmetric = Identity: Use for the handshake and authentication.
  3. TLS = Hybrid: Uses both to be both secure and fast.
  4. mTLS: Standard for Kubernetes internal security (both sides verify each other).
  5. Encryption: At-Rest and In-Transit must both be enabled for a hardened system.
