Authentication - Private CAs, TLS in k8s & mTLS

PRIVATE CAs​

Clusters secure communication between components using TLS certificates—and these are typically signed by an internal private Certificate Authority (CA).

Why use a Private CA?​

  • Internal Trust: Internal components don’t need public browser trust.
  • Efficiency: Faster issuance and rotation of certificates.
  • Automation: Certificates are often short-lived and auto-generated by the cluster during initialization.

One CA vs Multiple CAs​

StrategyAdvantagesUsed For
Single private CASimple managementMost standard clusters
Multiple CAsIsolates trust, reduces blast radiusLarge-scale or high-security clusters (Often etcd has a separate CA)

Why separate etcd CA?

  • etcd stores the full cluster state.
  • Isolating its CA limits the impact if the main Kubernetes CA is compromised.

Managed vs Self-Built Clusters​

  • kubeadm, k3s, GKE, EKS, AKS: Private CAs are automatically generated.
  • Kubernetes-the-Hard-Way: The administrator manually creates the root CA and signs all certificates.

Do Enterprises Use Public CAs Internally? No. Public CAs are only used for public-facing services (Ingress, Load Balancers, Gateway API). All Kubernetes internal component communication relies on private CAs.

KUBERNETES COMPONENTS AS CLIENTS AND SERVERS​

Key idea: The role (Client vs. Server) depends on who initiates the connection.

ComponentActs AsCommunicates With
kubectlClientAPI Server
SchedulerClientAPI Server
Controller-managerClientAPI Server
Kube-proxyClientAPI Server
KubeletClient or ServerClient when reporting to API server; Server when API server fetches logs/exec.
API ServerServer or ClientServer for all clients; Client when calling etcd or kubelets.
etcdAlways ServerAPI server only

Examples:

  • Kubelet reporting node status: Kubelet is the client, API server is the server.
  • kubectl logs: API server connects to the kubelet; API server is the client, Kubelet is the server.

mTLS in Kubernetes: Deep Dive​

To understand the TLS flow, everything required is stored in three main locations:

  1. Static pod manifests: /etc/kubernetes/manifests
  2. Kubeconfig files: /etc/kubernetes/*.conf (or inside pods)
  3. Kubelet directories: /var/lib/kubelet/

Typical File Locations:​

PurposePath
API server / scheduler / controller configs/etc/kubernetes/*.conf
Static pod manifests/etc/kubernetes/manifests
CA & certs for control plane/etc/kubernetes/pki
etcd certs/etc/kubernetes/pki/etcd
Kubelet certs/var/lib/kubelet/pki
Kube-proxy kubeconfig (in pod)/var/lib/kube-proxy

Examples of TLS Flow​

Example 1: Scheduler (client) ↔ API Server (server)​

1. Server-Side (API Server) Inspect the static pod manifest: cat /etc/kubernetes/manifests/kube-apiserver.yaml Flag: --tls-cert-file=/etc/kubernetes/pki/apiserver.crt

Check the certificate: openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text -noout

  • Subject: CN=kube-apiserver
  • Issuer: CN=kubernetes

2. How Scheduler Trusts API Server The scheduler uses a kubeconfig file: cat /etc/kubernetes/scheduler.conf Field: certificate-authority-data: <base64>

  • Decoding this shows the cluster root CA. The scheduler uses it to validate the API server’s certificate.

3. Client-Side (Scheduler Auth to API Server) The same scheduler.conf contains:

  • client-certificate-data
  • client-key-data

Decoded certificate:

  • Subject: CN=system:kube-scheduler
  • Issuer: CN=kubernetes

4. How API Server Verifies Scheduler In kube-apiserver.yaml: Flag: --client-ca-file=/etc/kubernetes/pki/ca.crt

  • Any client certificate signed by ca.crt is trusted.

Example 2: API Server (client) ↔ etcd (server)​

1. etcd Server Certificate cat /etc/kubernetes/manifests/etcd.yaml Flags:

  • --cert-file=/etc/kubernetes/pki/etcd/server.crt
  • --key-file=/etc/kubernetes/pki/etcd/server.key
  • --client-cert-auth=true
  • --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt

Inspect: openssl x509 -in /etc/kubernetes/pki/etcd/server.crt -text -noout

  • Subject: CN=
  • Issuer: CN=etcd-ca

2. How API Server Verifies etcd In kube-apiserver.yaml: Flag: --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt

3. API Server Client Certificate to etcd In kube-apiserver.yaml:

  • --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
  • --etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key

Certificate:

  • Subject: CN=kube-apiserver-etcd-client
  • Issuer: CN=etcd-ca

Example 3: API Server (client) ↔ Kubelet (server)​

Kubelet is NOT a Pod; it is a systemd process.

Find Config: ps -ef | grep kubelet Flag: --config=/var/lib/kubelet/config.yaml

Kubelet Certificates:

  • /var/lib/kubelet/pki/kubelet.crt
  • /var/lib/kubelet/pki/kubelet.key

Inspect: openssl x509 -in /var/lib/kubelet/pki/kubelet.crt -text -noout

  • Subject: CN=system:node:, O=system:nodes
  • Issuer: CN=

How Kubelet Got This Cert:

  1. Initially authenticates via bootstrap token.
  2. Submits a CSR (Certificate Signing Request).
  3. API server approves and signs.
  4. Kubelet obtains its long-term certificate.

Does API Server validate Kubelet server certificate? Not strictly. The API server already authenticated the node during bootstrap and issued its cert. Authorization protections (RBAC, Node authorizer, NodeRestriction) restrict behavior.

API Server’s Client Certificate to Kubelet: Flags in kube-apiserver.yaml:

  • --kubelet-client-certificate=/etc/kubernetes/pki/apiserver-kubelet-client.crt
  • --kubelet-client-key=/etc/kubernetes/pki/apiserver-kubelet-client.key
  • Subject: CN=kube-apiserver-kubelet-client
