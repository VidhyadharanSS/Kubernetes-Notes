Authentication: Kubeconfig and Kubernetes Contexts

KUBECONFIG AND KUBERNETES CONTEXTS​

What is a Kubeconfig File?​

The kubeconfig file is a configuration file used to configure access to Kubernetes clusters. It stores:

  • Cluster details: API server URL, Certificate Authority (CA) certificates.
  • User credentials: Authentication tokens, client certificates, and private keys.
  • Contexts: Specific combinations of a cluster, a user, and (optionally) a namespace.

Why is it used?

  • It enables kubectl to securely access clusters without requiring manual input (like server URLs or credentials) for every command.
  • Without it, the process of communicating with the API server would be lengthy, manual, and error-prone.

Kubernetes Contexts​

A context in kubeconfig links a cluster, a user, and a namespace. It allows for quick switching between different environments.

Example: A user named Seema can define three contexts to manage different environments:

  1. seema@dev-cluster-context
  2. seema@staging-cluster-context
  3. seema@prod-cluster-context

Each context simplifies management by specifying which cluster to talk to, which user credentials to use, and which namespace to target (e.g., app1-dev-ns, app1-staging-ns, app1-prod-ns).

Structure of a Kubeconfig File​

Typically stored at ~/.kube/config, the file includes:

  • Clusters: Defines the API server endpoint and the CA certificate used to verify the server.
  • Users: Includes client certificates and private keys used to authenticate the user to the cluster.
  • Contexts: The mapping that combines cluster and user settings.
  • Current-context: Indicates which context is currently active for kubectl commands.

Key Certificate Data Fields:

  • certificate-authority-data: Verifies the API server’s identity to the client.
  • client-certificate-data: Authenticates the user to the API server.
  • client-key-data: Proves the user’s identity securely. (Note: These fields contain Base64-encoded data).

Kubeconfig Example (YAML)​

apiVersion: v1
kind: Config
# Define the clusters
clusters:
- name: dev-cluster # Logical name for the development cluster
  cluster:
    server: https://dev-cluster-api-server:6443 # API server endpoint
    certificate-authority-data: <certificate-data> # Base64-encoded CA certificate
- name: staging-cluster
  cluster:
    server: https://staging-cluster-api-server:6443
    certificate-authority-data: <certificate-data>
- name: prod-cluster
  cluster:
    server: https://prod-cluster-api-server:6443
    certificate-authority-data: <certificate-data>

# Define users (credentials for authentication)
users:
- name: seema # Logical user name
  user:
    client-certificate-data: <client-cert-data> # Base64-encoded client certificate
    client-key-data: <client-key-data> # Base64-encoded private key

# Define contexts (combination of cluster + user + optional namespace)
contexts:
- name: seema@dev-cluster-context
  context:
    cluster: dev-cluster
    user: seema
    namespace: app1-dev-ns # Default namespace for this context
- name: seema@staging-cluster-context
  context:
    cluster: staging-cluster
    user: seema
    namespace: app1-staging-ns
- name: seema@prod-cluster-context
  context:
    cluster: prod-cluster
    user: seema
    namespace: app1-prod-ns

# Set the default context to use
current-context: seema@dev-cluster-context

Common kubectl config Commands​

TaskCommand
View current contextkubectl config current-context
List all contextskubectl config get-contexts
Switch contextkubectl config use-context <context-name>
View configkubectl config view
Set default namespacekubectl config set-context --current --namespace=<ns>
Add new userkubectl config set-credentials <user> --client-certificate=<cert> --client-key=<key>
Add new clusterkubectl config set-cluster <cluster> --server=<url> --certificate-authority=<ca>
Add new contextkubectl config set-context <context> --cluster=<cluster> --user=<user> --namespace=<ns>
Delete contextkubectl config delete-context <context>
Rename contextkubectl config rename-context <old> <new>

Managing Multiple Kubeconfigs​

You can manage multiple configuration files without merging them into one:

  1. Using the flag: kubectl get pods --kubeconfig=~/.kube/dev-kubeconfig
  2. Using the environment variable: export KUBECONFIG=$HOME/.kube/config:$HOME/.kube/custom-kubeconfig This ensures kubectl automatically uses and merges the specified configuration files.

Adding Entries Safely: Always use kubectl config commands to add clusters, users, or contexts instead of editing the file manually. This ensures data integrity and proper certificate embedding. Example sequence:

  1. Add a user
  2. Add a cluster
  3. Add a context
  4. Switch to the context
  5. Verify configuration using kubectl config view --minify

MUTUAL TLS (mTLS)​

mTLS enhances standard TLS by requiring both the client and the server to authenticate each other using certificates. This ensures mutual trust and secure communication between machines and services.

  • Standard TLS (1-Way): Only the server presents a certificate (typical for public websites).
  • mTLS (2-Way): Both sides present and verify certificates. This is ideal for Kubernetes internal service-to-service communication.

Managed Kubernetes services (EKS, GKE, AKS) use mTLS by default for internal communication between components like the kube-apiserver, kubelet, and etcd.

TLS (1-Way) vs. mTLS (2-Way)​

FeatureTLS (1-Way)mTLS (2-Way)
AuthenticationServer onlyBoth client and server
Use CasePublic websites, APIsMicroservices, Kubernetes, APIs w/ clients
Identity VerificationServer proves identityMutual identity verification
Certificate RequiredOnly server certificateBoth server and client certificates
