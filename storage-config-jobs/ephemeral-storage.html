ephemeral-storage

VOLUMES - EPHEMERAL STORAGE​

Ephemeral storage refers to storage that is temporary, meaning any data written to it only lasts for the duration of the Pod's lifetime. When the Pod is deleted, the data is also lost.

Types of Ephemeral Storage​

TypeScope/LifetimeKey FeatureUse Cases
EmptyDirExists for the lifetime of the Pod on the node's storage.Enables data sharing between containers in a Pod. Each Pod replica gets its own unique volume.Scratch Space, Caching, Temporary persistence.
Downward APIExists for the lifetime of the Pod.Allows Pods to access metadata about themselves (name, namespace, labels, resource limits). Injected via Environment Variables or mounted files.Dynamic configuration, Self-Awareness, Offloading API server calls.
ConfigMap & SecretData exists independently but is mounted/injected for the Pod's lifetime.Inject configuration data (ConfigMap) and sensitive data (Secret) into Pods.Decoupling configuration from application code.

EMPTYDIR EPHEMERAL STORAGE​

  • emptyDir is an empty directory created when a Pod is assigned to a node.
  • It exists only for the lifetime of the Pod and enables inter-container file sharing within that Pod.
  • If defined in a Deployment, each Pod replica gets its own unique emptyDir volume.
  • It is ideal for workloads requiring isolated, temporary scratch space that does not need to persist beyond the Pod's lifecycle.

Why is EmptyDir Used?​

It is ideal for:

  • Scratch space (Temporary workspace for processing, caching, or temporary computations where data persistence isn't required).

Writable vs Read-Only Layers in Containers​

  • If multiple containers in a Pod share the same image, they share the read-only image layers to save space.
  • Each container still gets its own writable layer where file changes are stored (delta data), isolated from other containers.
  • Sharing Data: By mounting the same emptyDir volume into multiple containers, they gain access to a shared writable space during the Pod's lifetime.

Example EmptyDir Pod: This example demonstrates two containers sharing a volume mounted at /data.

apiVersion: v1
kind: Pod
metadata:
  name: emptydir-example # Name of the Pod.
spec:
  containers:
  - name: busybox-container # Container 1
    image: busybox
    command: ["/bin/sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: temp-storage
      mountPath: /data # Mount point inside the container
  - name: busybox-container-2 # Container 2
    image: busybox
    command: ["/bin/sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: temp-storage
      mountPath: /data
  volumes:
  - name: temp-storage # Name must match volumeMounts
    emptyDir: {}       # Creates a temporary directory tied to the Pod's life

Verification Steps:

  1. Create a file from Container 1: 
    kubectl exec emptydir-example -c busybox-container -- sh -c 'echo "What a file!" > /data/myfile.txt'
  2. Read the file from Container 2: 
    kubectl exec emptydir-example -c busybox-container-2 -- cat /data/myfile.txt
    # Expected Output: What a file!

DOWNWARD API​

The Downward API allows Pods to dynamically access metadata about themselves or their environment (Pod name, namespace, labels, annotations, resource limits). This metadata is injected as Environment Variables or mounted files via volumes.

Why is it Used?

  • Dynamic Configuration: Applications can retrieve Pod-specific metadata (like its own assigned IP or labels) at runtime.
  • Self-Awareness: Makes Pods aware of their environment, including their name, namespace, and resource constraints.
  • Simplifies Configuration Management: Eliminates the need for manual configuration by providing metadata directly to the containers.

Downward API Examples​

1. Using Environment Variables (fieldRef):​

Injects metadata directly as an environment variable into the container.

apiVersion: v1
kind: Pod
metadata:
  name: downwardapi-example
  labels:
    app: demo
spec:
  containers:
  - name: metadata-container
    image: busybox
    command: ["/bin/sh", "-c", "env && sleep 3600"]
    env:
    - name: POD_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.name # Pulls Pod's name
    - name: POD_NAMESPACE
      valueFrom:
        fieldRef:
          fieldPath: metadata.namespace # Pulls Pod's namespace

Verification:

kubectl exec downwardapi-example -- env | grep POD_
# Expected Output:
# POD_NAME=downwardapi-example
# POD_NAMESPACE=default

2. Using Files via Volumes (projected volume):​

Injects metadata as files into a mounted volume. This allows a process to read metadata by reading a file, often used for configuration bootstrapping.

apiVersion: v1
kind: Pod
metadata:
  name: downwardapi-volume
  labels:
    app: good_app
    owner: hr
  annotations:
    version: "good_version"
spec:
  containers:
  - name: metadata-container
    image: busybox
    command: ["/bin/sh", "-c", "cat /etc/podinfo/* && sleep 3600"]
    volumeMounts:
    - name: downwardapi-volume
      mountPath: /etc/podinfo # Files are visible here
  volumes:
  - name: downwardapi-volume
    downwardAPI:
      items:
      - path: "labels"
        fieldRef:
          fieldPath: metadata.labels # Writes Pod labels to /etc/podinfo/labels
      - path: "annotations"
        fieldRef:
          fieldPath: metadata.annotations # Writes Pod annotations to /etc/podinfo/annotations

Verification using Pod Logs: The Pod's command dumps the content of these files to its logs on startup.

kubectl logs downwardapi-volume
# Expected Output will include:
# app="good_app"
# owner="hr"
# version="good_version"

CONFIGMAPS AND SECRETS​

  • Overview: ConfigMaps and Secrets are Kubernetes objects designed to inject configuration data and sensitive information into Pods, respectively.
  • Volume Behavior: When mounted as volumes, the data is temporary and only available for the Pod's lifetime (similar to emptyDir).
  • Why are they Used?
    • They allow the decoupling of configuration from application code.
    • They enable the secure injection of sensitive data, simplifying management across multiple Pods.
