Storage - Ephemeral Storage

Ephemeral storage refers to storage that is temporary, meaning any data written to it only lasts for the duration of the Pod's lifetime. When the Pod is deleted or evicted, the data is lost.

Types of Ephemeral Storage​

TypeScope/LifetimeKey FeatureUse Cases
EmptyDirPod LifecycleCreated on the node's local disk or RAM. Enables inter-container data sharing.Scratch space, caching, large temporary computations.
Downward APIPod LifecycleExposes Pod metadata (IP, Name, Labels) to the container.Dynamic configuration, logging, self-awareness.
ConfigMap & SecretIndependent but mounted per PodInjects configuration or sensitive data into the Pod filesystem.Decoupling config from code, managing credentials.
Generic Ephemeral VolumesPod LifecycleAllows using PVC-like features (snapshotting, specific backends) for temporary storage.High-performance temporary storage requiring specific disk types (SSD).

1. EMPTYDIR EPHEMERAL STORAGE​

  • An emptyDir volume is first created when a Pod is assigned to a Node, and exists as long as that Pod is running on that node.
  • Inter-container Sharing: All containers in the Pod can read and write the same files in the emptyDir volume.
  • Isolation: If a Deployment has 3 replicas, each Pod gets its own isolated emptyDir. They do not share data between Pods.

Performance Tip: RAM-backed emptyDir​

By default, emptyDir is stored on the node's disk (HDD/SSD). For high-performance workloads, you can force it into the node's RAM (tmpfs).

Note: RAM-backed storage counts against the container's memory limit. If the node reboots, the data is wiped.

Example YAML (Disk vs. RAM):

apiVersion: v1
kind: Pod
metadata:
  name: cache-pod
spec:
  containers:
  - name: nginx
    image: nginx
    volumeMounts:
    - name: ram-storage
      mountPath: /cache
  volumes:
  - name: ram-storage
    emptyDir:
      medium: Memory # This forces the storage into RAM (tmpfs)
      sizeLimit: "1Gi" # Optional: Prevents the Pod from consuming too much RAM

2. DOWNWARD API​

The Downward API allows Pods to access their own metadata without making calls to the Kubernetes API server.

Why use it?

  • Security: Containers don't need a ServiceAccount with API permissions just to find out their own name or IP.
  • Configuration: Useful for logging agents that need to tag logs with the Pod Name or Namespace.

Implementation Methods​

Method A: Environment Variables (fieldRef)​

env:
- name: MY_POD_IP
  valueFrom:
    fieldRef:
      fieldPath: status.podIP

Method B: Volume Files (downwardAPI volume)​

This creates a file inside the container containing the metadata value.

volumes:
- name: pod-info
  downwardAPI:
    items:
    - path: "labels"
      fieldRef:
        fieldPath: metadata.labels

3. CONFIGMAPS AND SECRETS AS VOLUMES​

While often used as environment variables, mounting them as volumes is more robust:

  1. Dynamic Updates: If a ConfigMap is updated, the file inside the Pod is eventually updated by the Kubelet (usually within 60 seconds) without a Pod restart. (Env vars require a restart).
  2. Binary Data: Secrets can store binary files (like SSH keys or certificates) which are difficult to handle as env vars.

4. GENERIC EPHEMERAL VOLUMES (Advanced)​

Introduced to provide "scratch space" that supports features usually reserved for Persistent Volumes (like specific StorageClasses or Snapshots).

  • They are created when the Pod is created and deleted when the Pod is deleted.
  • They allow you to request a specific amount of space (e.g., 20Gi) from a specific storage provider (e.g., EBS or local-path).
spec:
  containers:
  - name: app
    image: busybox
    volumeMounts:
    - mountPath: /scratch
      name: ephemeral-scratch
  volumes:
  - name: ephemeral-scratch
    ephemeral:
      volumeClaimTemplate:
        spec:
          storageClassName: "gp3" # Use a specific fast SSD class
          accessModes: [ "ReadWriteOnce" ]
          resources:
            requests:
              storage: 2Gi

5. RESOURCE MANAGEMENT: EPHEMERAL STORAGE LIMITS​

Just like CPU and Memory, you can (and should) manage how much disk space a Pod can consume on the node's local disk to prevent one Pod from filling up the entire node.

spec:
  containers:
  - name: app
    resources:
      requests:
        ephemeral-storage: "1Gi"
      limits:
        ephemeral-storage: "2Gi"
  • Request: Used by the scheduler to find a node with enough disk space.
  • Limit: If the Pod exceeds this (via emptyDir or container logs), the Kubelet will evict the Pod.

Key Summary for Preparation​

  1. Lifetime: Always tied to the Pod. If the Pod dies/is deleted, the data is gone.
  2. emptyDir: Use for data sharing between containers in one Pod.
  3. RAM disk: Use medium: Memory for sub-millisecond latency caching.
  4. Limits: Always set ephemeral-storage limits in production to prevent "No space left on device" errors on your nodes.
  5. Downward API: It is the "Self-Awareness" tool for Pods.
