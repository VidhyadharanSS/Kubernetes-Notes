Storage - Volumes - Persistent storage - PV, PVC, Storage classes.

VOLUMES - PERSISTENT STORAGE - PART II​

PERSISTENT VOLUMES (PV)​

  • A PV is a piece of storage in your cluster that has been provisioned either manually by an administrator or dynamically using Storage Classes.
  • PVs exist independently of Pod lifecycles and can be reused or retained even after the Pod is deleted. They have properties such as capacity, access modes, and reclaim policies.

PERSISTENT VOLUME CLAIMS (PVC)​

  • A PVC is a request for storage by a user. It functions similarly to how a Pod requests compute resources. When a PVC is created, Kubernetes searches for a PV that meets the claim's requirements.

Binding Process:​

  1. Administrator: Provisions PVs (or sets up Storage Classes for dynamic provisioning).
  2. Developer: Creates a PVC in the Pod specification requesting specific storage attributes.
  3. Kubernetes: Binds the PVC to a suitable PV, thereby making the storage available to the Pod.

Pods rely on Node resources—such as CPU, memory, and network—to run containers. On the other hand, when a Pod requires persistent storage, it uses a PersistentVolumeClaim (PVC) to request storage from a PersistentVolume (PV), which serves as the actual storage backend.

Points to Note:​

1. PVs are Cluster-Scoped Resources​

  • A PersistentVolume (PV) is a cluster-wide resource, just like Nodes or StorageClasses.
  • This means it is not tied to any specific namespace, and it can be viewed or managed from anywhere within the cluster.
  • You can verify this using: 
    kubectl api-resources | grep persistentvolume
    This shows that the resource persistentvolumes has no namespace, indicating it's cluster-scoped.

2. PVCs are Namespace-Scoped​

  • A PersistentVolumeClaim (PVC), on the other hand, is a namespaced resource, just like Pods or Deployments.
  • This means it exists within a specific namespace and is only accessible by workloads (Pods) within that namespace.
  • You can verify this using: 
    kubectl api-resources | grep persistentvolumeclaim
  • Example: If you have a namespace called app1-ns and a PVC is created there and binds to a PV, only Pods in app1-ns can use that PVC. If a Pod in app2-ns tries to reference the same PVC, it will fail because the PVC is invisible outside its namespace.

3. 1-to-1 Binding Relationship Between PVC and PV​

  • A PVC can bind to only one PV.
  • Similarly, a PV can be bound to only one PVC.
  • This is a strict one-to-one relationship, ensuring data integrity and predictable access control.
  • Once a PV is bound, its claimRef field is populated, and it cannot be claimed by any other PVC unless explicitly released.
  • claimRef: This is a field in a PersistentVolume (PV) that records which PersistentVolumeClaim (PVC) has successfully claimed it. It includes details like the PVC’s name and namespace. This field ensures that the PV is not mistakenly claimed by any other PVC.

4. PVCs request storage​

  • PVs fulfill that request if they match capacity, access mode, and storage class.
  • Once a PVC is bound, it remains bound until:
    • The PVC is deleted.
    • The PV is manually reclaimed or deleted (depending on the reclaim policy).
  • The reclaim policy (Retain, Delete, or deprecated Recycle) determines what happens to the PV after the PVC is deleted.

KUBERNETES PERSISTENT STORAGE FLOW (MANUAL PROVISIONING)​

Access modes in Persistent Volumes:​

Access ModeDescriptionExample Use CaseType of Storage & Examples
ReadWriteOnce (RWO)The volume can be mounted as read-write by a single node. Multiple Pods can access it only if they are on the same node.Databases that require exclusive access but may run multiple replicas per node.Block Storage (e.g., Amazon EBS, GCP Persistent Disk, Azure Managed Disks)
ReadOnlyMany (ROX)The volume can be mounted as read-only by multiple nodes simultaneously.Sharing static data like configuration files or read-only datasets across multiple nodes.File Storage (e.g., NFS, Azure File Storage)
ReadWriteMany (RWX)The volume can be mounted as read-write by multiple nodes simultaneously.Content management systems, shared data applications, or log aggregation.File Storage (e.g., Amazon EFS, Azure File Storage, On-Prem NFS)
ReadWriteOncePod (RWOP) (v1.29+)The volume can be mounted as read-write by only one Pod across the entire cluster.Ensuring exclusive access to a volume for a single Pod, such as in tightly controlled workloads.Block Storage (e.g., Amazon EBS with RWOP enforcement)

Storage Types​

Block Storage​

  • Ideal for: Databases and applications requiring low-latency, high-performance storage. It provides raw storage blocks that applications can format and manage as individual disks.
  • Examples: Amazon EBS, GCP Persistent Disk, Dell EMC Block Storage.
  • Key Characteristic: Block storage is generally node-specific and does not support simultaneous multi-node access.
  • Access Modes: Commonly used with ReadWriteOnce or ReadWriteOncePod.
  • Analogy: Like attaching a USB drive to a single computer—it provides fast, reliable storage but cannot be shared concurrently across multiple systems.

File Storage​

  • Ideal for: Shared storage scenarios where multiple Pods or applications need simultaneous access to the same data. It is mounted as a shared filesystem.
  • Examples: Amazon EFS, Azure File Storage, On-Prem NFS (Network File System).
  • Key Characteristic: Purpose-built for multi-node concurrent access.
  • Access Modes: Often supports ReadOnlyMany or ReadWriteMany.

Reclaim policies:​

Reclaim PolicyBehaviorBest Use CaseCommon in
DeleteDeletes PV and storage resource when PVC is deleted.Cloud-based dynamically provisioned storage.AWS EBS, GCP PD, Azure Disk.
RetainKeeps PV and storage, requiring manual cleanup.Backup, auditing, manual data recovery.On-prem storage, long-term retention workloads.
Recycle (Deprecated)Cleans volume and makes PV available again.(Not recommended)Previously used in legacy systems.

PV AND PVC BINDING CONDITIONS​

ConditionRequirement for Binding
Storage Class MatchstorageClassName of PVC and PV must match (or both can be empty).
Access Mode CompatibilityPVC's requested access mode must be supported by PV.
Sufficient CapacityPV's storage must be ≥ PVC's requested capacity.
Volume Binding ModeEither Immediate or WaitForFirstConsumer.
Volume StatePV must be in Available state to bind.
Matching Volume ModePVC and PV must have the same volumeMode (Filesystem or Block).
Claim ReferenceIf PV has a claimRef, it can only bind to that specific PVC.

DEMO - PV AND PVC​

1. Delete existing storage classes:

kubectl delete sc --all

2. Create a PV (example-pv.yaml):

apiVersion: v1
kind: PersistentVolume
metadata:
  name: example-pv # Unique name for the PV
spec:
  capacity:
    storage: 5Gi # Total storage provided
  accessModes:
    - ReadWriteOnce # Mounted as read-write by a single node
  persistentVolumeReclaimPolicy: Retain # Retain the volume and data after PVC deletion
  hostPath:
    path: /mnt/data # Uses a directory on the node (for demo purposes only)

Note: When ReclaimPolicy is set to Retain, the PV and its data will not be deleted if the PVC is removed. The storage is preserved for manual recovery and must be handled by an admin before reuse.

3. Create a PVC (example-pvc.yaml):

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: example-pvc # Unique name for the PVC
spec:
  accessModes:
    - ReadWriteOnce # Request volume to be mounted as read-write by a single node
  resources:
    requests:
      storage: 2Gi # Ask for at least 2Gi of storage

Note: Since this PVC doesn't specify a StorageClass, it binds to a compatible PV. The 5Gi PV created above is a suitable candidate for this 2Gi claim.

4. Create the Pod referencing the PVC (example-pod.yaml):

apiVersion: v1
kind: Pod
metadata:
  name: example-pod
spec:
  containers:
    - name: nginx-container
      image: nginx
      volumeMounts:
        - mountPath: /usr/share/nginx/html # Directory inside container where volume is mounted
          name: persistent-storage # Logical name for the volume mount
  volumes:
    - name: persistent-storage # Volume name referenced above
      persistentVolumeClaim:
        claimName: example-pvc # Bind this volume to the previously created PVC

When this Pod is created, Kubernetes binds the PVC to the PV and mounts the volume. The PVC status changes from "Pending" to "Bound".

Important Note on Deletion: To delete a PV or PVC, you must delete the Pod first, then the PVC, and finally the PV. Otherwise, resources may remain in a "Terminating" state due to Kubernetes safety mechanisms.

Verification Commands:

kubectl get pv
kubectl describe pv example-pv
kubectl get pvc
kubectl describe pvc example-pvc
kubectl describe pod example-pod

STORAGE CLASSES​

A Storage Class in Kubernetes defines different storage configurations, enabling dynamic provisioning of PVs. It eliminates the need to manually pre-create PVs.

  • Purpose: Define storage backends (disk types), reclaim policies, and binding modes.
  • Dynamic Provisioning: When a PVC is created, Kubernetes uses the referenced Storage Class to automatically provision a corresponding PV.
  • Flexibility: Multiple Storage Classes (e.g., high-performance SSDs, low-cost HDD) can coexist.

Note: StorageClass replaces manual PV provisioning. However, attributes like accessModes, size, and volumeMode are still defined in the PVC.

AWS EBS Storage Class Examples:​

General Purpose (gp3):

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc-gp3
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

High Performance (io1):

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc-io1
provisioner: ebs.csi.aws.com
parameters:
  type: io1
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

STORAGE CLASSES - DEMO​

PVC Creation:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: example-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi

Even if no storageClassName is specified, Kubernetes defaults to the "standard" StorageClass (if configured as default). The PVC status remains "Pending" until a Pod is created.

Verify Default StorageClass:

kubectl describe sc standard

Look for the annotation: storageclass.kubernetes.io/is-default-class: "true".

The WaitForFirstConsumer Binding Mode:​

This mode is critical because it delays PV creation until a Pod is scheduled.

  • Cost Optimization: Ensures resources aren't provisioned until actually needed.
  • Zonal Awareness: In multi-AZ environments (like AWS), it ensures the volume is created in the same Availability Zone where the Pod is scheduled. Without this, a PVC might trigger volume creation in AZ-1 while the Pod is scheduled in AZ-2, making the volume inaccessible.

Pod referencing the PVC:

apiVersion: v1
kind: Pod
metadata:
  name: example-pod
spec:
  containers:
    - name: nginx-container
      image: nginx
      volumeMounts:
        - mountPath: /usr/share/nginx/html
          name: persistent-storage
  volumes:
    - name: persistent-storage
      persistentVolumeClaim:
        claimName: example-pvc

Once the Pod is created, Kubernetes finds the PVC, provisions a PV using the default StorageClass, and the PVC status changes to Bound.

Final Verification:​

# Check PVs
kubectl get pv
# Example output: pvc-24d1f4ee... 2Gi RWO Delete Bound default/example-pvc

# Check PVCs
kubectl get pvc
# Example output: example-pvc Bound pvc-24d1f4ee... 2Gi RWO standard
