Kubernetes - Daemonsets, Jobs and CronJobs

DAEMONSETS​

  • Purpose: Ensures that a specific Pod runs on every node (or a selected subset of nodes). It automatically manages Pod creation/deletion as nodes are added to or removed from the cluster.
  • Self-Healing: If you delete a Pod created by a DaemonSet manually, the DaemonSet controller will immediately recreate it to maintain the desired state.
  • Control Plane Scheduling:
    • In managed cloud clusters (EKS, GKE, AKS), DaemonSets usually do not run on control plane nodes.
    • On self-managed clusters, they can run on control plane nodes if the node has taints (e.g., node-role.kubernetes.io/control-plane:NoSchedule) and proper tolerations are configured in the Pod spec.
  • Common Use Cases:
    1. Monitoring Agents: Prometheus Node Exporter, Datadog agent.
    2. Logging Agents: Fluentd, Fluent Bit, Filebeat.
    3. Networking Plugins: Calico, Flannel, Cilium.
    4. Storage Plugins: AWS EBS CSI, GCP PD CSI Drivers.

Example: kube-proxy​

kube-proxy is deployed as a DaemonSet to ensure every node has networking functionality. Verification commands:

kubectl get daemonsets.apps -n kube-system kube-proxy
kubectl get pods -n kube-system -o wide | grep -i kube-proxy

Tolerations in kube-proxy: Generally, it uses the following:

tolerations:
- operator: Exists

Note: An operator of "Exists" with no key specified means the Pod tolerates any taint on the node—regardless of key, value, or effect. This ensures it can be scheduled everywhere.

DEMO: Logging DaemonSet​

Step 1: Create a New Namespace​

kubectl create namespace logging-ns

Step 2: Switch Context​

kubectl config set-context --current --namespace=logging-ns

Step 3: Apply the DaemonSet​

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
  namespace: logging-ns
  labels:
    app: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      tolerations:
      - key: "node-role.kubernetes.io/control-plane"
        operator: "Exists"
        effect: "NoSchedule"
      containers:
      - name: log-collector
        image: busybox
        command: ["/bin/sh", "-c", "while true; do echo 'Collecting logs...'; sleep 30; done"]
        resources:
          requests:
            cpu: "50m"
            memory: "50Mi"
          limits:
            cpu: "100m"
            memory: "100Mi"
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
          type: Directory

Note: This uses hostPath to access the node's /var/log. In production, logs are usually shipped to external storage (S3, NFS) or platforms (ElasticSearch, Loki).

JOBS​

  • Purpose: A Job creates one or more Pods to run a specific task to completion. Once the task finishes successfully (Status = Completed), the Job is finished.
  • Retries: If a Pod fails, the Job controller automatically retries the task based on the backoffLimit.
  • Success: If a Pod succeeds, the Job does not restart it.
  • Use Cases: Batch jobs, database migrations, generating reports.

DEMO: Create a Job​

apiVersion: batch/v1
kind: Job
metadata:
  name: hello-job
spec:
  ttlSecondsAfterFinished: 60 # Automatically deletes the job object 60s after completion
  completions: 2              # Total successful completions needed
  parallelism: 2              # Number of Pods that can run concurrently
  backoffLimit: 4             # Retries before marking the job as failed
  template:
    spec:
      containers:
      - name: hello
        image: busybox
        command: ["/bin/sh", "-c", "echo Hello from the Job! && sleep 10"]
      restartPolicy: Never    # Jobs usually use 'Never' or 'OnFailure'

Key Logic: Kubelet vs. Job Controller​

  • Kubelet: Responsible for restarting containers within a Pod (if restartPolicy is Always/OnFailure). It does not recreate Pods.
  • Job Controller: Detects failed Pods (at the API level) and decides whether to create a new Pod based on the backoffLimit.
  • restartPolicy: Never: The Pod transitions to Failed phase on error, and the Job controller creates a new Pod.

CRONJOBS​

  • Purpose: Allows you to schedule Jobs to run at specific times (like Linux crontab).
  • Use Cases: Backups, nightly reports, cleanup tasks, scheduled notifications.
  • Logic: It acts as a scheduler that creates a Job object at the specified time.

Cron Expression Fields:​

PositionFieldAllowed Values
1Minute0–59
2Hour0–23
3Day of Month1–31
4Month1–12
5Day of Week0–6 (0 = Sunday)
  • * : Every value.
  • /5 : Every 5 units (steps).
  • 1,3,5 : Specific list.
  • 1-5 : Range.

Common Expressions:​

  • */5 * * * * : Every 5 minutes.
  • 0 * * * * : Every hour at minute 0.
  • 0 2 * * * : Every day at 2 AM.
  • 0 0 * * 0 : Every Sunday at midnight.

Note: Kubernetes CronJobs use UTC time internally.

DEMO: CronJob Manifest​

apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello-cronjob
spec:
  schedule: "*/1 * * * *" # Every minute
  jobTemplate:
    spec:
      backoffLimit: 4
      template:
        spec:
          containers:
          - name: hello
            image: busybox
            command: ["/bin/sh", "-c", "echo Hello from CronJob!"]
          restartPolicy: Never
