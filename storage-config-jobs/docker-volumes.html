Storage - Docker Volumes Revisited

Docker Image Layers and Storage​

Docker images are built from a series of layers.

Dockerfile Instructions​

  1. Layer-Creating Instructions: These instructions create a new layer in the image.
    • Examples: FROM, RUN, COPY, ADD.
    • Note: Having many of these increases the final image size. Multi-stage builds are recommended to separate build-time instructions (which create layers) from runtime instructions, producing smaller, optimized images.
  2. Non-Layer-Creating Instructions: These modify the behavior or metadata of the layer they are executed on, without creating a new layer themselves.
    • Examples: CMD, ENTRYPOINT, WORKDIR, EXPOSE, ENV, LABEL, USER, VOLUME, STOPSIGNAL, ARG.

Image Layering and Writable Layer​

  • The layers created by FROM, RUN, ADD, etc., are Read-Only for all containers started from that image.

  • When a container runs, any new files created or changes made are stored in a writable layer on the Docker Host. This is called delta data.

  • Storage Usage Example: If the base image is 50MB, and Container 1 adds 4MB of delta data, the total storage used by Container 1 is 54 MB.

  • Ephemeral Data: Since the delta data lives only in the writable layer, if the container is stopped or fails, this data is lost. A mechanism is needed to persist data beyond the container's lifecycle.

  • Inspection: You can inspect the layers and storage history using: docker inspect history <image>

DOCKER STORAGE​

Docker manages storage using two primary driver types:

Storage Drivers (Internal/Ephemeral Data)​

  • Handles: The container's internal ephemeral data (data tied to the container's lifecycle).
  • Concept: Think of these as the Filesystems for Containers, managing the file organization within the container's root filesystem.
  • Kubernetes Parallel: Kubernetes largely uses the same concepts for ephemeral container data.
  • Examples (Common Drivers):
    • OverlayFS (Default on modern Linux systems).
    • ZFS (Advanced Storage).
    • AUFS (Legacy Driver).
    • Btrfs (For Large-Scale Environments).

Checking Storage Driver: Run docker info to check the storage driver used by the Docker host.

Volume Drivers (External/Persistent Data)​

  • Handles: External persistent data that exists independently of the container's lifecycle.
  • Concept: Think of these as External Hard Drives for Containers.
  • Kubernetes Parallel: Kubernetes manages this via Persistent Volumes (PVs), which are managed at the cluster-level rather than container-level.
  • Examples:
    • Local (Default Docker Volume Driver).
    • NFS
    • Cloud-specific drivers like AWS EBS or Azure Disks.

Kubernetes Integration: Kubernetes uses CSI (Container Storage Interface) drivers to connect to cloud storage providers like AWS EBS, Azure Disks, or NFS, integrating them as PVs/PVCs. For temporary data, Kubernetes still relies on storage drivers similar to Docker (e.g., overlay2).

Docker Installation Context (On Mac, Windows, Linux)​

OSDocker Engine RequirementStorage Location
LinuxRuns natively, no virtualization layer required.Storage/volumes created directly on host filesystem: /var/lib/docker/volumes.
macOSDocker Desktop uses a Linux VM via the Apple Virtualization Framework (previously HyperKit).Storage is inside the managed Linux VM.
WindowsDocker Desktop uses WSL 2 (Windows Subsystem for Linux) to run the Linux kernel.Storage is within the WSL 2 environment.
  • Key takeaway: Docker Engine requires a native Linux kernel, which is why direct installation isn't possible on macOS or Windows without a virtualization/subsystem layer.

DOCKER VOLUMES (PERSISTENCE)​

Since container data in the writable layer is ephemeral (lost when the container is deleted), Docker volumes are used to persist data beyond the container lifecycle.

  • Default Storage Location: /var/lib/docker/volumes on the Docker host.

Creating and Using a Volume​

  1. Create a Docker volume: 
    docker volume create my-vol
  2. Run a container attached to the volume: 
    docker run -d --name my-cont-1 -v my-vol:/app my-image
  3. Create data inside the container: 
    docker exec -it my-cont-1 bash
    cd /app
    echo "This is my delta data" > file.txt
    cat file.txt # Output: This is my delta data
  4. Verify Persistence: Delete the container and check the volume data directly on the host. 
    docker rm -f my-cont-1
    sudo cat /var/lib/docker/volumes/my-vol/_data/file.txt 
    # Output: This is my delta data
    The data persists even though the container is gone.

TYPES OF DOCKER VOLUMES​

TypeUse CaseProsCons
Named VolumeDefault Docker-managed volumes (e.g., my-vol).Easy to use, portable, survives container deletion.Abstracted path, may need extra step for backups.
Bind MountMount a specific host directory to the container.Full control, real-time syncing, easy for dev work.Tied to host path, can cause permission issues.
tmpfs MountTemporary in-memory mount (data lost on restart).Fast, doesn't write to disk.Data not persistent, only useful for short-term use.

Preference:

  • Named Volumes are preferred in most production use-cases because they are managed, portable, and persistent.
  • Bind Mounts are useful for development/local testing to sync code from your machine into the container.
