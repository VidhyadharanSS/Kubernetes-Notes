Storage - Persistent Storage

Persistent Storage refers to data that exists independently of any single Pod's lifecycle.

EVOLUTION OF STORAGE IN KUBERNETES:​

Kubernetes storage management has evolved from In-Tree plugins to the modern CSI standard.

1. In-Tree Volume Plugins (Legacy Model - Deprecated)​

  • Historically: Storage Drivers were embedded directly in the Kubernetes core.
  • Drawbacks:
    • Maintenance was cumbersome and tied to Kubernetes release cycles.
    • Vendors could not independently develop or release updates.
    • Bugs in storage drivers could affect the Kubernetes core functionality.
  • Examples (Legacy): AWS EBS, Google Persistent Disk, Azure Disk and File Storage, Cinder, Ceph.
  • Example PV (In-Tree): Note the driver specification within the spec. 
    apiVersion: v1
    kind: PersistentVolume
    metadata:
      name: in-tree-pv
    spec:
      capacity:
        storage: 10Gi
      accessModes:
        ReadWriteOnce
      awsElasticBlockStore: # Legacy in-tree driver section
        volumeID: vol-0abcd1234efgh5678
      fsType: ext4

Note: Most in-tree plugins were officially deprecated starting with Kubernetes 1.21.

2. CSI Backed (Container Storage Interface) - The Modern Standard​

  • CSI: Developed by the CNCF, it decouples storage driver development from the Kubernetes core.
  • Key Benefits of CSI:
    • Independent Updates: Vendors can release drivers without waiting for Kubernetes core updates.
    • Faster Development: Features and fixes are delivered more quickly.
    • Flexibility: Supports advanced capabilities like snapshotting, resizing, cloning, and monitoring.
    • Easy Integration: Simpler for vendors to develop custom drivers.
  • Confirmation: Check the provisioner field in the StorageClass or look at csidrivers to confirm a CSI driver is in use.
  • Example PV (CSI Backed): Note the modern csi section. 
    apiVersion: v1
    kind: PersistentVolume
    metadata:
      name: csi-pv
    spec:
      capacity:
        storage: 10Gi
      accessModes:
        ReadWriteOnce
      storageClassName: gp3-sc # Links to a StorageClass that uses a CSI driver
      csi: # Modern CSI driver section
        driver: ebs.csi.aws.com
        volumeHandle: vol-0abcd1234efgh5678
      fsType: ext4
  • Object Storage Note: Kubernetes does not natively support mounting Object Storage (like Amazon S3, Azure Blob Storage) as volumes because it operates differently from file systems. Applications should use vendor-specific SDKs or APIs to interact with object storage.

STORAGE TYPES IN CSI BACKED​

CSI drivers enable access to different types of storage:

1. File Storage​

  • Structure: Stored in a hierarchical structure (folders/directories). Also known as shared storage.
  • Access: Requires file name + full file path to retrieve a file.
  • Examples: Used in NAS (Network Attached Storage). Protocols include NFS and SMB.
  • Characteristics: Simple, easy, and inexpensive.

2. Block Storage​

  • Usage: Used for large and structured files like databases and applications.
  • Structure: The file is divided into multiple blocks, each with a unique ID. Blocks can be spread across different disk drives.
  • Examples: Commonly used with SAN (Storage Area Network). Protocols include iSCSI and FC (Fibre Channel).
  • Characteristics: Faster and more flexible than file storage, but more complex.

3. Object Storage​

  • Usage: Used for large amounts of unstructured data.
  • Components: Every object has 3 parts: ID (unique identifier), metadata (description), and data (actual data).
  • Access: Easily available via HTTP Requests.
  • Use Cases: Storing static content like photos, music, backups, etc.

HOSTPATH PERSISTENT STORAGE​

  • Mechanism: A hostPath volume mounts files or directories directly from the host node's filesystem into the Pod.
  • Node-Specific: hostPath volumes are limited to the node where the Pod is scheduled. All Pods on the same node can access the data, but Pods on different nodes cannot share the same hostPath.
  • Use Cases: Debugging, accessing host-level files (logs, configuration), or sharing specific host resources with containers.

Why Kubernetes Recommends Avoiding hostPath​

  • Security Risks: Pods can potentially access sensitive host files if the path is misconfigured.
  • Limited Portability: Being tied to a specific node reduces scheduling flexibility—the Pod can only run on the node that has the data.
  • Better Alternatives: PersistentVolumes (PV) with PersistentVolumeClaims (PVC) or Local Persistent Volumes are recommended for persistent data as they offer better control and security abstraction.

Understanding hostPath in KIND (Linux VM context)​

When running Kubernetes in environments like KIND (which uses a Docker container as a node, running on macOS/Windows):

PlatformDocker Engine Runs OnhostPath Points To
Ubuntu/LinuxNativelyHost's actual filesystem (e.g., /tmp/hostfile)
macOS/WindowsLinux VM via DockerFilesystem inside the Kubernetes node container (the Linux VM)

Example hostPath Pod:

apiVersion: v1
kind: Pod
metadata:
  name: hostpath-example
spec:
  containers:
  - name: busybox-container
    image: busybox
    command: ["sh", "-c", "cat /data && sleep 3600"] # Reads /data
    volumeMounts:
    - name: host-volume
      mountPath: /data # Container mounts host file here
  volumes:
  - name: host-volume
    hostPath:
      path: /tmp/hostfile
      type: FileOrCreate # If the file doesn't exist on the host, create it.
  • Data Population: Data is written to the host file via the container: 
    kubectl exec -it hostpath-example -- sh -c 'echo "Hey you!!" > /data'
  • Verification: A second Pod scheduled on the same node can read the data: 
    kubectl exec hostpath-verify -- cat /data 
    # Expected Output: Hey you!!

Hostpath Types: File, FileOrCreate, Directory, DirectoryOrCreate, Socket, BlockDevice.​
