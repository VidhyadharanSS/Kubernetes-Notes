Kubernetes Scheduling: Deep Dive

1. NODE MAINTENANCE: Cordon, Uncordon, and Drain​

Managing the cluster requires the ability to safely remove nodes for updates or repairs.

  • kubectl cordon <node>: Marks the node as unschedulable. It does not affect existing pods.
  • kubectl uncordon <node>: Reverses a cordon, allowing the scheduler to place new pods on the node again.
  • kubectl drain <node>: The professional way to empty a node. It cordons the node and evicts all running pods.
    • Safeguard Flags:
      • --ignore-daemonsets: Since DaemonSets run on every node, they can't be "moved." This flag is required to bypass them.
      • --delete-emptydir-data: Required if pods use local emptyDir volumes (the data will be deleted).
      • --force: If there are pods not managed by a Controller (naked pods), you must use this to delete them.

2. TAINTS AND TOLERATIONS (Node Repulsion)​

Concept: A Node "Taint" tells pods: "Stay away unless you have a specific pass (Toleration)."

Taint Effects​

  1. NoSchedule: (Hard) New pods without toleration will never be scheduled here.
  2. PreferNoSchedule: (Soft) The system tries to avoid placement but will land here if no other nodes are available.
  3. NoExecute: (Eviction) New pods are blocked, AND existing pods without the toleration are immediately kicked off the node.

YAML Example: Tolerating a GPU Taint​

If a node is tainted with hardware=nvidia-tesla:NoSchedule:

spec:
  tolerations:
  - key: "hardware"
    operator: "Equal"
    value: "nvidia-tesla"
    effect: "NoSchedule"

3. NODE SELECTOR & NODE AFFINITY (Node Attraction)​

Node Selector (The Legacy Way)​

Simple key-value matching. If the label isn't there, the pod stays Pending.

spec:
  nodeSelector:
    disktype: ssd

Node Affinity (The Advanced Way)​

Node Affinity provides complex logic and levels of "strictness."

Hard Rule: requiredDuringSchedulingIgnoredDuringExecution​

The pod must meet these criteria, or it will remain in a Pending state.

spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values: ["us-east-1a", "us-east-1b"]

Soft Rule: preferredDuringSchedulingIgnoredDuringExecution​

A "Best Effort" approach. You provide a Weight (1-100). The scheduler adds up weights for nodes that match and picks the highest score. If no nodes match, the pod is scheduled anyway.

spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values: ["ssd"]

Node Anti-Affinity​

To ensure a pod never lands on specific nodes, use NotIn or DoesNotExist inside a Hard Rule.

    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: NotIn
          values: ["master-node"]

4. POD AFFINITY AND ANTI-AFFINITY (Inter-Pod Relationship)​

This schedules pods based on the labels of other Pods already running on the node.

  • Pod Affinity: "Run me where app: frontend is running" (Co-location for performance).
  • Pod Anti-Affinity: "Do NOT run me where app: database is running" (Separation for HA).

The topologyKey Concept​

This defines the scope of "closeness."

  • kubernetes.io/hostname: The same physical node.
  • topology.kubernetes.io/zone: The same Availability Zone.

YAML Example: High Availability (Anti-Affinity)​

Ensure two instances of the same app never run on the same node.

spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web-server
        topologyKey: "kubernetes.io/hostname"

5. TOPOLOGY SPREAD CONSTRAINTS (Even Distribution)​

While Anti-Affinity is "all or nothing," Topology Spread Constraints allow you to distribute pods evenly across zones or nodes to prevent bottlenecks.

Key Fields:​

  1. maxSkew: The maximum difference in pod count between any two domains. maxSkew: 1 is ideal for balance.
  2. whenUnsatisfiable:
    • DoNotSchedule: Hard rule (Pod stays Pending if balance can't be met).
    • ScheduleAnyway: Soft rule (Still tries to balance but will schedule if it can't).

YAML Example: Spreading across 3 Zones​

spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: "topology.kubernetes.io/zone"
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: api-service

6. COMPARISON: HARD VS. SOFT RULES​

FeatureHard Rule (required...)Soft Rule (preferred...)
StrictnessMandatory Requirement.Preference/Wishlist.
Failure ResultPod remains Pending.Pod schedules on any available node.
Use CaseCompliance, Hardware requirements (GPU), Safety.Cost optimization, "Nice-to-have" performance boosts.
Scheduling OverheadLow (Quickly filters nodes).Higher (Must calculate and compare weights).

7. CRITICAL PREP SUMMARY Table​

FeatureLogicDirectionTarget
TaintsRepulsionNode $\rightarrow$ PodRepels non-tolerant pods.
TolerationsImmunityPod $\rightarrow$ NodeAllows pods to stay on tainted nodes.
Node AffinityAttractionPod $\rightarrow$ NodeForces/Prefers pods to specific nodes.
Pod AffinityCo-locationPod $\rightarrow$ PodPuts pods together (App + Cache).
Pod Anti-AffinitySeparationPod $\rightarrow$ PodKeeps pods apart (HA Replicas).
Topology SpreadBalancingPod $\rightarrow$ DomainSpreads pods evenly (Zone/Rack/Node).

Exam Tip: "IgnoredDuringExecution"​

All Affinity and Spread rules have the suffix IgnoredDuringExecution. This means if a pod is already running and the labels on the node or other pods change, Kubernetes will NOT evict the pod. Only Taints with NoExecute will cause active eviction.
